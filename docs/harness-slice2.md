> **상태 (2026-11-26):** 오너가 승인 통로, ID 규칙, 시험 대상, N00을 미루는 것을 정했고, 명세가 제안한 여섯 가지도 그대로 승인했습니다. 구현 1~9단계를 마쳤습니다. 9단계에서 두 도구로 스토리부터 Stage 2 끝까지 실제로 돌렸고(각본 PO), 오너가 PO가 되어 휴대폰에서 검토 페이지를 보고 채팅으로 답한 실제 실행(「회원 가입」)도 끝까지 갔습니다. 그 실행에서 찾은 하네스 문제 다섯 가지를 고쳤습니다(아래 「구현하며 확인할 것」). PR #7로 main에 머지해 조각 2를 마쳤습니다(2026-11-26). 첫 조각은 [harness-slice1.md](harness-slice1.md)에, 설계의 근거는 [harness-design.md](harness-design.md)에 있습니다.

## 범위

- **하는 것:** 작업 유형 `backend`, N01~N04(N03W·N03F는 건너뜀), N11~N15, 스테이지 패킷 0 → 1과 1 → 2, 검토 페이지와 채팅 승인, Stage 2에서 스펙·설계로 돌아가는 길, 프로젝트 전체 ID, 작업 세션은 Claude와 Codex 두 도구
- **하지 않는 것:** N00, Figma 노드, 모바일, Stage 3·4, N2D, 스토리 여러 개를 한 스프린트에 넣기, N12와 머지의 사람 표본, 검토 페이지의 승인 버튼, 채팅 밖의 입력 통로. 다음 조각에서 차례로 붙입니다(아래 「다음 조각」).

첫 조각의 원장, 잠금, 관문, 횟수 제한, 실패 원인 분류는 그대로 씁니다. 새로 만드는 것은 사람 노드(N01, N04)와 승인 대기, 검토 페이지, 패킷, 스테이지 세션입니다.

## 구조

```
PO ─ 채팅 ─▶ PO 창구 (Claude 세션) ─┬─▶ 4dd story ─▶ N01 스토리
                                    ├─▶ 4dd run ─▶ 지휘 프로그램 ─▶ 작업 세션 · 리뷰 세션 · 관문
                                    ├─▶ 4dd review ─▶ 검토 페이지 ─▶ 아티팩트 게시 ─▶ PO
                                    └─▶ 4dd human approve · reject (PO의 말 그대로)
```

| 부분 | 하는 일 |
|---|---|
| PO 창구 | 오너가 프로젝트 폴더에서 여는 Claude 세션입니다. PO의 말을 `4dd` 명령으로 옮기고, 검토 페이지를 아티팩트로 게시하고, PO의 답을 그대로 원장에 남깁니다. 하네스가 띄운 세션이 아니라서 노드를 처리하지 않습니다 |
| 지휘 프로그램 | 첫 조각과 같습니다. Stage 0부터 시작해 N04와 N15에서 멈추고(사람 대기), 승인되면 이어 갑니다 |
| 작업 세션 | Stage 0과 Stage 1에서는 스테이지마다 하나, Stage 2에서는 작업마다 하나 씁니다 |
| 리뷰 세션 | N13 설계와 N14 작업 목록을 읽기 전용으로 확인합니다(L1). N27처럼 매번 새로 띄웁니다 |
| 검토 페이지 | `4dd review`가 승인할 파일로 만드는 한 장짜리 HTML입니다. 무엇을 보여 줬는지 해시로 남깁니다 |

|---|---|---|---|---|

- **사람 노드:** N01과 N04, N15의 승인은 지휘 프로그램이 멈추고(`wait_human`, 이유 `review`) 기다리는 자리입니다. 지휘 프로그램은 기다리며 돌지 않고 끝납니다(종료 코드 3). PO 창구가 답을 남긴 뒤 `4dd run`을 다시 부릅니다.
- **횟수 제한:** 작업 세션 노드는 첫 조각과 같습니다(노드 연속 3회). Stage 0·1에는 작업이 없으므로 작업 전체 한도(10회)를 기능 하나에 겁니다. 사람이 판정하는 N04와 N15 승인에는 횟수 제한을 걸지 않고, 되돌림 수는 보고서가 셉니다.
- **Stage 2에서 돌아갈 때:** 첫 조각에서는 사람이 스펙이나 설계를 직접 고쳤습니다. 이제 [workflow.md](workflow.md#실패-원인)대로 갑니다. `spec_ambiguous`·`spec_missing_state`는 PO가 돌아가기를 승인한 뒤 N02 → N03 → N04 → 원래 작업의 N22로, `arch_wrong`은 승인 뒤 N13 → N14 → N15 → N21로 갑니다. 돌아온 N02는 요구사항을 더하거나 빼지 않습니다.

### 파일 형식

- **`story.md`:** PO의 말을 고치지 않고 그대로 둡니다. 맨 위에 기능 이름과 사람 개입 ID만 붙입니다.
- **`spec.md`:** 첫 조각의 형식(`## 목적`, `## 요구사항`의 `- R4 …` 줄, `## 범위 밖`, `## 제약`)에 `## 물을 것`을 더합니다. 물을 것은 PO가 동작으로 답할 수 있는 질문만 적습니다. 기술 결정(토큰 저장 방식 같은 것)은 N13이 정합니다.
- **`sprint.md`:** `## 목표`(한 문장), `## 기능`(이번 스프린트에 넣은 기능 폴더), `## 백로그`(`- T4`처럼 작업 ID를 할 순서대로).
- **`design.md`, `tasks.md`:** 첫 조각과 같습니다. `design.md`에 `## 기존 기능에 주는 영향`을 더해, 새 기능이 고치는 기존 코드와 규칙을 적습니다.

### `nodes.yaml`에 더하는 것

```yaml
N02:
  name: 요구사항 스펙 작성
  stage: 0
  method: sdd
  kind: work
  actor: worker
  session: stage               # stage: 스테이지마다 하나 · task: 작업마다 하나 (Stage 2)
  instruction: instructions/N02.md
  reads: [story, other_specs, ids, hint]
  writes: ["specs/{feature}/spec.md"]
  gate:
    checks: [spec_sections, ids_unique]

N04:
  name: 스펙과 시나리오 리뷰 및 승인
  stage: 0
  method: sdd
  kind: decision
  actor: human
  review: [story, spec, scenarios]      # 검토 페이지에 넣을 것
  approve: {packet: "0-1", requires: [no_open_questions]}
  on_fail:
    - when: [spec_ambiguous, spec_missing_state]
      goto: N02                         # 그다음은 파일 순서대로 N03 → N04

N13:
  name: 설계 스펙 작성
  stage: 1
  method: sdd
  kind: work
  actor: worker
  session: stage
  instruction: instructions/N13.md
  reads: [spec, scenarios, other_designs, src_map, hint]
  writes: ["specs/{feature}/design.md"]
  gate:
    checks: [design_sections]
    review: instructions/N13.review.md  # 리뷰 세션(L1), 읽기 전용, 매번 새로

N15:
  name: 스프린트 백로그 확정
  stage: 1
  method: scrum
  kind: work
  actor: worker
  session: stage
  instruction: instructions/N15.md
  reads: [sprint, tasks]
  writes: ["specs/sprint.md"]
  gate:
    checks: [backlog_ids]
  review: [sprint, design, tasks, review_results]
  approve: {packet: "1-2"}
  on_reject: [N11, N13, N14, N15]       # PO가 고칠 곳으로 고를 수 있는 노드
```

- **`actor: human`:** 사람이 하는 노드입니다. 지시문과 세션이 없고, 지휘 프로그램은 그 자리에서 멈춥니다.
- **`session`:** 작업 세션을 어떻게 나눌지입니다. 스테이지가 바뀌면 새 세션을 띄웁니다.
- **`{feature}`:** 지금 기능 폴더 이름으로 바뀝니다. 다른 기능의 파일은 고칠 수 없습니다.
- **`gate.review`:** 관문의 기계 검사를 통과한 뒤 리뷰 세션이 판정합니다. N27과 같은 형식(통과 여부와 한국어 의견 목록)으로 답하고, 의견은 다음 차례의 맥락에 붙습니다.
- **`review`와 `approve`:** 노드가 통과하면 사람 승인을 기다립니다. 승인되면 패킷을 남기고 다음 노드로, 되돌리면 `on_fail`(판단 노드)이나 `on_reject`(작업 노드)로 갑니다.
- **형식 검사에 더하는 것:** 사람 노드에는 지시문이 없어야 하고, `approve`가 있으면 패킷 경계가 있어야 하고, `on_reject`의 노드는 같은 스테이지에 있어야 합니다.

### 노드 지시문

N02, N03, N11, N13, N14, N15와 리뷰 지시문 둘(`N13.review.md`, `N14.review.md`)을 첫 조각과 같은 네 칸(목표, 할 것, 하지 말 것, 주의점)으로 씁니다.

- **N02:** 스토리의 말을 요구사항으로 옮기고 지어내지 않습니다. 스토리로 정할 수 없는 동작은 「물을 것」에 질문으로 남깁니다. 다른 기능의 요구사항과 겹치거나 부딪치면 그 ID를 적습니다.
- **N03:** 요구사항마다 성공과 실패 시나리오를 쓰고, 화면 대신 API 응답으로 확인하게 씁니다.
- **N13:** 기존 기능의 `design.md`와 `src/` 구조를 따르고, 기존 코드를 고쳐야 하면 「기존 기능에 주는 영향」에 적습니다.
- **N14:** 작업마다 맡는 시나리오가 있게 나눕니다(시나리오는 그 요구사항의 마지막 작업이 통과시킴). 「이미 충족」이 나오지 않게 작업끼리 겹치지 않게 합니다.

`4dd context`가 넣는 읽을거리에 `story`, `spec`, `other_specs`(다른 기능의 요구사항 줄), `other_designs`, `src_map`(소스 파일 목록), `ids`(이번 기능에서 쓸 다음 번호), `sprint`, `review_results`를 더합니다. 첫 조각처럼 원장에는 넣은 것의 ID와 해시만 남깁니다.

## PO 창구

오너가 프로젝트 폴더에서 여는 Claude 세션(데스크톱, 원격 포함)이 PO 창구입니다. `4dd init`이 프로젝트에 넣는 스킬 `4dd-po`(`.claude/skills/4dd-po/SKILL.md`)를 따릅니다. 하네스가 띄운 작업 세션은 슬래시 명령과 스킬을 끈 채 돌아서 이 스킬을 쓰지 못합니다.

1. PO가 스토리를 말하면 기능 이름(영문 소문자와 `-`)을 정해 `4dd story --feature password-reset "<PO의 말 그대로>"`를 부르고 `4dd run`을 돌립니다.
2. 지휘 프로그램이 N04에서 멈추면 `4dd review`로 검토 페이지를 만들고 아티팩트로 게시한 뒤 링크를 PO에게 보냅니다. 같은 기능의 다음 검토는 같은 아티팩트를 고쳐 게시하고, 주소는 `4dd review --url`로 남깁니다.
3. PO의 답을 옮깁니다. 승인이 분명하면 `4dd human approve --review RV3 --quote "<PO의 말>"`, 고칠 점이나 물을 것의 답이면 `4dd human reject --review RV3 --cause spec_missing_state --quote "<PO의 말>"`입니다. 애매하면 PO에게 다시 묻습니다.
4. `4dd run`을 다시 돌립니다. N15에서 같은 순서를 한 번 더 하고, 그다음은 Stage 2가 끝날 때까지 갑니다.
5. Stage 2가 사람을 부르면(횟수 초과, 스펙이나 설계 원인) 무엇이 막혔는지 PO가 알아들을 말로 전하고 답을 옮깁니다.

창구는 PO 대신 판단하지 않습니다. 승인은 PO의 말에 승인이 분명히 있을 때만 남기고, PO의 말은 고치지 않고 그대로 남깁니다(`.4dd/human/<ID>.md`, 원장에는 해시). 개발자는 같은 명령을 터미널에서 직접 불러도 되고, 그때는 `channel: terminal`로 남습니다.

### 검토 페이지

- **N04 페이지:** 스토리(PO의 말), 요구사항 카드(`R` 칩과 문장, 이어진 시나리오 칩), 시나리오 카드(조건·만일·그러면 줄), 물을 것(노랑), 범위 밖, 답하는 법.
- **N15 페이지:** 스프린트 목표, 백로그 레인(작업 카드에 `R`·`S` 칩), 설계 요약(API, 데이터 모델, 기존 기능에 주는 영향), N13·N14 리뷰 결과, 추적 검사 결과.
- **공통:** 하네스가 파일에서 바로 만들어 토큰이 들지 않습니다. 맨 위에 검토 ID와 해시 앞 8자를, 맨 아래에 원문 펼쳐 보기를 둡니다. 아티팩트 규칙(두세 단어 제목, 밝은 화면과 어두운 화면의 색, 휴대폰 폭에서 가로로 넘치지 않음, 바깥 스크립트 없음)을 지키는 한 파일로 만들고, 마크다운은 `marked`로 바꿉니다.
- **검토 해시:** 페이지에 넣은 파일들의 경로와 해시를 묶은 값입니다. 승인할 때 지금 파일로 다시 계산해 다르면 거부합니다. PO가 본 것과 승인된 것이 같게 하기 위해서입니다.
- **읽는 사람:** 코드를 모르는 PO가 읽을 수 있게 씁니다. ID 칩은 두되 문장은 평범한 말로 씁니다.

### 승인과 되돌림

- **N04 승인:** 패킷 0 → 1을 남기고 스토리, 스펙, 시나리오의 기준 해시를 고정합니다.
- **N04 되돌림:** PO의 말이 힌트가 되어 N02부터 다시 합니다. 원인은 `spec_ambiguous`(뜻이 모호함)나 `spec_missing_state`(빠진 경우가 있음)이고, 창구가 PO의 말을 보고 고릅니다.
- **N15 승인:** 패킷 1 → 2를 남기고 설계, 작업 목록, 스프린트 파일의 기준 해시를 고정합니다. 이어서 N21이 백로그 순서대로 작업을 고릅니다.
- **N15 되돌림:** 창구가 PO의 말로 고칠 곳을 고릅니다(목표나 백로그는 N11이나 N15, 설계는 N13, 작업 나누기는 N14). 원인 단어는 쓰지 않습니다(N12 → N01과 같음). 고친 노드부터 순서대로 다시 갑니다.
- **학습 후보:** 되돌림에 남긴 PO의 말은 `learnings.yaml`에 후보로 더합니다. 근거는 검토 ID와 사람 개입 ID입니다.

## 승인을 지키는 겹

```
작업 세션의 셸 훅 ─▶ 사람 명령의 세션 검사 ─▶ 차례 뒤 원장 검사 ─▶ 검토 해시 ─▶ 기준 해시
```

- **작업 세션의 셸 훅:** 하네스가 띄운 세션이 `4dd human`, `4dd story`, `4dd review`를 부르면 막습니다(셸 명령 검사에 더함). 가장 빨리 막아 차례를 아낍니다. 지금은 이 명령들을 막지 않습니다.
- **사람 명령의 세션 검사:** 이 명령들은 하네스 세션 표시(`FOURDD_NODE`)가 있으면 아무것도 하지 않고 실패합니다.
- **차례 뒤 원장 검사:** 결정적인 겹입니다. 작업 세션의 한 차례 동안 원장에 훅 실행 기록 말고 다른 줄(사람 개입, 검토, 패킷)이 덧붙었으면 멈춥니다. 첫 조각의 원장 지키기를 그대로 씁니다.
- **검토 해시:** 승인은 그 검토 페이지의 해시가 지금 파일과 같을 때만 됩니다. 페이지를 보낸 뒤 파일이 바뀌었으면 새 페이지를 만들어 다시 받습니다.
- **기준 해시:** 승인 뒤 승인 없이 바뀐 스펙이나 설계는 다음 노드를 시작할 때 걸립니다(첫 조각과 같음).

창구가 PO의 말을 잘못 옮기는 것은 기계로 막을 수 없는 남은 틈입니다. PO의 말 원문을 남겨 나중에 대조할 수 있게 하고, 각본으로 돌린 승인은 `by: script`로 따로 셉니다.

## 스테이지 패킷과 기준 해시

- **패킷:** 원장의 `packet` 줄입니다. 경계(`0-1`, `1-2`), 기능, 파일과 해시, 담긴 ID(`R4`~`R6`, `S4`~`S7` 같은 것), 승인한 검토 ID를 적습니다.
- **다음 스테이지:** 패킷에 든 파일만 믿고 출발합니다. `4dd context`가 패킷의 해시와 지금 파일을 비교하고, 다르면 멈춥니다(재사용 전 검증).
- **기준 해시:** 노드가 통과해 커밋하면 그 노드가 쓴 파일(`writes`)의 기준 해시를 새로 적습니다. 그 뒤로는 다른 노드가 고칠 수 없고, 바꾸려면 사람 승인을 거칩니다. 첫 조각에서 N29의 `tasks.md`에만 하던 것을 모든 노드로 넓힙니다.
- **이미 있는 기능:** 첫 조각에서 `4dd init`이 고정하던 패킷 1 → 2는 이제 N15 승인이 남깁니다. 시험 프로젝트에 이미 있는 로그인 기능의 패킷은 `4dd init`이 남깁니다.

## 프로젝트 전체 ID

- `R`, `S`, `T`는 기능을 넘어 프로젝트 전체에서 한 번씩만 씁니다. 새 기능은 프로젝트에서 가장 큰 번호 다음부터 씁니다.
- `4dd ids`가 다음 번호를 알려 주고, `4dd context`가 N02, N03, N14에 「이번 기능에서 쓸 ID」로 넣습니다.
- `4dd check trace`는 기능 폴더마다 하던 검사에 더해 프로젝트 전체의 겹침을 오류로 잡습니다. `--stage 0`은 요구사항과 시나리오만 봅니다(N03 관문, 작업 목록이 아직 없음).
- 인수 테스트 파일 이름, 커밋 트레일러, 원장의 형식은 바뀌지 않습니다(`tests/acceptance/S4.test.ts`, `4DD-Refs: R4,S4`).

## 시험 프로젝트

- **`harness/fixtures/login-reset/`:** 로그인 기능(T1~T3)이 끝난 상태입니다. 첫 조각 실행 결과에서 `src/`, `tests/`, 체크된 `tasks.md`를 가져오고, 로그인 테스트가 모두 통과해야 합니다.
- **스토리:** 시험 프로젝트에 넣지 않고 `harness/fixtures/login-reset.story.md`에 둡니다. PO 창구가 `4dd story`로 넣는 것까지 시험하기 위해서입니다.

  > 비밀번호를 잊은 사용자가 이메일로 받은 재설정 링크로 새 비밀번호를 정할 수 있으면 좋겠어요. 링크는 30분만 쓸 수 있고 한 번 쓰면 끝이에요. 잠긴 계정도 비밀번호를 바꾸면 풀렸으면 해요.

  로그인의 잠금 규칙(`R2`)과 맞물려서 기존 설계와 코드를 읽어야 하고, "이메일로 받은"처럼 백엔드 범위를 정해야 하는 곳(메일을 실제로 보내나)이 있어 「물을 것」이 나올 만한 스토리입니다.
- **각본 PO:** 반복 실행용으로 PO의 답을 정해 둔 `harness/fixtures/login-reset.po.yaml`(물을 것에 대한 답, 첫 N04에서 한 번 되돌림, 그다음 승인)을 둡니다. 각본 PO의 개입은 `by: script`로 남겨 사람 개입 수에 넣지 않습니다.

## `4dd` 명령

| 명령 | 누가 부르나 | 하는 일 | 종료 코드 |
|---|---|---|---|
| `4dd story --feature <이름> "<글>"` | PO 창구 | N01: `specs/<이름>/story.md`를 쓰고 사람 개입(`story`)을 남김. 진행 중인 기능이 있으면 거부 | 0 · 1 잘못된 입력 |
| `4dd review [--url <주소> [--id <ID>]]` | PO 창구 | 기다리는 승인(N04, N15)의 검토 페이지를 `.4dd/review/<ID>.html`로 만들고 `review`를 남김. `--url`은 게시한 주소를 남김(사람 대기 시간의 시작점) | 0 · 1 기다리는 승인 없음 |
| `4dd human approve ["<PO의 답>"]` | PO 창구 | Stage 2에서 스펙·설계 원인으로 멈췄을 때 돌아가기를 승인. PO의 답은 돌아간 N02·N13의 맥락이 됨 | 0 · 1 기다리는 중이 아님 |
| `4dd human approve --review <ID> --quote "<글>"` | PO 창구 | 검토 해시를 확인하고 승인, 패킷과 기준 해시를 남김 | 0 · 1 해시가 다름이나 물을 것이 남음 |
| `4dd human reject --review <ID> (--cause <원인> \| --to <노드>) --quote "<글>"` | PO 창구 | 되돌림을 남기고 PO의 말을 다음 차례의 힌트와 학습 후보로 넘김 | 0 · 1 잘못된 입력 |
| `4dd ids` | 사람 · 지휘 프로그램 | 다음 `R`, `S`, `T` 번호 | 0 |
| `4dd init <폴더> --fixture login-reset` | 사람 | 시험 프로젝트를 고르고 `4dd-po` 스킬을 넣음 | 0 · 1 오류 |
| `4dd run` · `4dd status` | PO 창구 | Stage 0부터 진행하고 승인 대기에서 멈춤. `status`는 기다리는 검토와 주소를 보여 줌 | 첫 조각과 같음 |
| `4dd check trace [--stage 0]` | 관문 · 사람 | 프로젝트 전체의 ID 겹침까지 검사 | 0 통과 · 2 막음 |

## 원장 이벤트

첫 조각의 이벤트 9종에 셋을 더하고 셋을 넓힙니다.

| 이벤트 | 언제 | 주요 필드 |
|---|---|---|
| `review` (새로) | 검토 페이지를 만들거나 게시함 | `id`(`RV`), `action`(`built`, `published`), `node`, `feature`, `files`(경로와 해시), `hash`, `url` |
| `await_human` (새로) | 사람 승인이나 스토리를 기다리기 시작함 | `node`, `task`, `feature`, `reason`(`review`, `story`, `not_ready`). 지휘 프로그램은 이 줄을 남기고 끝남 |
| `packet` (새로) | N04와 N15 승인 | `id`(`PK`), `boundary`(`0-1`, `1-2`), `feature`, `files`, `refs`, `review` |
| `human` (넓힘) | 사람 개입 | `review`, `by`(`po`, `dev`, `script`), `channel`(`chat`, `terminal`), `quote`(해시), `to`(N15 되돌림), `kind`에 `story` 더함 |
| `node_start` · `node_end` (넓힘) | 노드 진입과 종료 | `feature` (Stage 0·1에는 작업이 없음) |
| `run_start` (넓힘) | `4dd run` 시작 | `stage` (시작한 스테이지) |

- **사람 대기 시간:** 검토 페이지를 게시한 때(`review`의 `url`)와 그 검토에 대한 `human` 사이의 시간입니다. 기다리는 동안 지휘 프로그램은 돌지 않습니다.
- **`state.json`:** 지금 기능과 스테이지, 기다리는 검토 ID, 스테이지 세션 ID를 더합니다.

| 4 | 사람 명령: `4dd story`, `4dd review`(검토 페이지), `4dd human approve·reject --review`, 검토 해시, 사람 명령 막기 | 파일을 바꾼 뒤 승인이 거부되고, 작업 세션의 훅 입력으로 부른 `4dd human`이 막힘 |
| 5 | 노드 지시문(N02, N03, N11, N13, N14, N15와 리뷰 둘)과 `4dd context`의 새 읽을거리 | Claude로 N02 한 차례를 돌리고 원장에 `loaded`가 남음 |
| 6 | 지휘 루프: Stage 0 → 1 → 2, 승인 대기와 재개, Stage 2에서 스펙·설계로 돌아가기 | 각본 PO로 스토리부터 Stage 2 끝까지 감 |
| 7 | PO 창구 스킬 `4dd-po`와 검토 페이지 게시 | 검토 페이지가 휴대폰 폭에서 읽힘 (창 없는 브라우저로 확인) |
| 8 | `4dd report`에 더하는 질의 | 원장만으로 위 질의 결과가 나옴 |
| 9 | 완료 기준 전체 | 아래 「완료 기준」 |

각본 PO와 Claude로 6단계까지 먼저 끝내고, 오너가 PO가 되는 실제 실행과 Codex는 그다음에 합니다. 한 도구, 한 PO로 루프가 돌기 전에 여럿을 함께 맞추면 원인을 가르기 어렵기 때문입니다(첫 조각과 같은 이유).

- **Codex 실제 실행 (확인함):** 같은 스토리로 끝까지 돌려 작업 4개를 첫 통과율 100%, 되돌림 0번으로 끝냈습니다(테스트 24개). 사람 개입 1번은 아래 N14 리뷰 문제 때문이었습니다. **고친 하네스로 다시 돌린 Codex 실행은 사람 개입 0번**(각본 PO의 스토리·되돌림·승인 두 번만), 판단 노드 첫 통과율 100%, 되돌림 0번, 테스트 22개 통과입니다.
- **찾아 고친 것 1 (재사용 전 검증):** Stage 0·1의 노드는 잠긴 `specs/`를 고칩니다. 그 노드가 실패해 다시 할 때 지난 차례가 남긴 파일을 「승인 없이 바뀐 기준」으로 보고 멈췄습니다. 이제 돌 노드가 고칠 수 있는 파일은 이 검사에서 뺍니다.
- **찾아 고친 것 2 (리뷰의 실패 기준):** Codex의 N14 리뷰 세션이 매번 설계의 세부(함수 이름, 경로)를 작업 문장에 더 옮기라고 해서 세 번 실패했습니다. N13·N14 리뷰 지시문에 실패시키는 기준을 적고, 그 밖의 의견은 통과시키며 참고로 적게 했습니다.
- **찾아 고친 것 3 (리뷰 지적이 여럿일 때):** Claude의 T8은 「이미 충족」이라 N27 리뷰가 빠진 판단 여럿을 찾았는데, N23이 되돌아올 때마다 하나씩만 테스트해 연속 3번 한도를 다 썼습니다. N23은 지적마다 실패 테스트를 한 차례에 모두 쓰게 했습니다.
- **비용 관찰:** 같은 세션을 이어 쓸수록 차례당 가격이 올랐습니다(스펙 차례 $0.09 → $0.60, Stage 2의 N25 무렵 $0.8). 작업이 7개인 기능에서 Stage 2가 비용의 대부분입니다. 조각 5(학습 승격)의 개선 후보입니다.
- **오너가 PO인 실제 실행 (확인함, 2026-11-26):** 오너가 창구가 제안한 시나리오 세 가지 가운데 「회원 가입」을 골라 스토리를 채팅으로 넣었습니다. 작업 세션은 Claude입니다. 검토 페이지는 기능 하나에 아티팩트 하나로, 같은 주소에 네 번(RV1~RV4) 고쳐 게시했습니다.
  - Stage 0: 스펙이 물을 것 6개를 남겼고, 오너는 「여섯가지 다 알아서 정해주고, 정한것을 알려줘」라고 답했습니다. 에이전트가 정한 문장마다 「(PO가 맡겨 정함)」을 붙였고, 아이디 규칙이 요구사항(R9)으로 하나 늘었습니다. 요구사항 6개(R4~R9), 시나리오 11개(S4~S14)로 승인됐습니다.
  - Stage 1: 설계 리뷰와 작업 나누기 리뷰가 첫 차례에 통과했고, 작업 5개(T4~T8)로 승인됐습니다. T4는 회원 저장소를 로그인 코드에서 떼어 내는 기존 기능 손보기입니다.
  - Stage 2: T6에서 승인된 스펙끼리의 모순이 드러났습니다(아이디는 4~20자인데 가입이 되는 예시 아이디 `lee`는 3자). 사람이 원인을 `spec_ambiguous`로 바로잡고, 오너가 「규칙 유지, 예시 수정」으로 답해 스펙으로 돌아갔다가(N02 → N03 → N04 다시 승인) T6의 N22로 돌아왔습니다. 작업 5개를 모두 끝냈고 프로젝트 테스트 89개(로그인 포함)가 통과합니다.
  - 사람 개입 8번: 계획대로인 것 4번(스토리, 물을 것의 답, N04 승인, N15 승인), 스펙 모순 때문 3번(원인 바로잡기, 오너의 답, N04 다시 승인), 하네스 문제 때문 1번(힌트). 오너가 검토 페이지에 답하기까지 걸린 시간은 0.7~8.4분입니다.
  - 비용(표시 가격): 모두 약 $27.2로 적었지만 누적 금액을 더한 값이었고, 다시 센 값은 약 $7.8입니다(Stage 0·1 약 $1.1, Stage 2 약 $6.7, 2026-11-27). Stage 0·1 약 $2.7, 스펙으로 돌아간 차례 약 $0.5, Stage 2 약 $24. 작업 T6 하나가 $11.5입니다(아래 비용 관찰).
- **찾아 고친 것 4 (상태 보기):** PO 창구 스킬은 모든 명령에 `--root`를 붙이는데 `4dd status`만 폴더를 위치 인자로 받아 「시작하지 않았습니다」라고 답했습니다. 같은 실행에서 상태의 기능 이름이 지금 작업의 기능(signup) 대신 첫 기능 폴더(login)로 나왔습니다. 둘 다 고쳤습니다.
- **찾아 고친 것 5 (PO가 답을 맡길 때):** N02 지시문은 「지어내지 말고 물을 것으로 남긴다」뿐이라, PO가 답을 맡기면 같은 질문을 다시 남길 수 있었습니다. 맡긴 질문은 흔하고 안전한 쪽으로 정하고 「(PO가 맡겨 정함)」을 붙여 검토 페이지에서 알아보게 했습니다.
- **찾아 고친 것 6 (구현 중 스펙 모순):** N24가 「코드로는 못 고치고 스펙을 정해야 한다」고 세 번 답했는데, 작업 노드에서 원인을 바로잡으면 같은 노드를 다시 하기만 했습니다. [workflow.md](workflow.md)의 「횟수 제한」대로, 작업 노드(N23~N25)를 사람이 앞 스테이지 원인으로 바로잡으면 같은 스테이지의 뒤 판단 노드(N26, N27)의 그 원인 경로를 씁니다. 다시 승인받으면 원래 작업으로 돌아오고, 보고서는 이것도 「Stage 2에서 돌아감」으로 셉니다. 같은 모순을 막으려고 N03 지시문에 「예시 값은 요구사항의 모든 규칙을 따르고, 규칙이 생기면 기존 시나리오의 예시도 다시 본다」를 넣었습니다. N13 리뷰는 이런 모순을 실패시키지 않고 참고 지적으로 남기며, N15 검토 페이지가 그것을 PO에게 보여 줍니다.
- **찾아 고친 것 7 (스펙이 바뀐 뒤의 옛 단위 테스트):** 돌아온 T6에서 앞 작업(T5)의 단위 테스트가 옛 예시 `lee`를 써서 N28이 실패했습니다. N23은 그 테스트를 `lee01`로 바르게 고쳤지만, 관문이 「실패하는 새 테스트」를 요구해 세 번 거절했습니다. N23에 `reentry: spec_changed`를 두었습니다. 그 작업이 N04에서 다시 승인받은 뒤 N23이 아직 통과하지 않았으면, 실패를 요구하지 않고 기존 단위 테스트를 새 스펙에 맞게 고친 것도 받습니다(테스트 수는 줄면 안 됨).
- **찾아 고친 것 8 (힌트가 지워짐):** `4dd human hint`가 힌트 글과 학습 후보를 쓰고 커밋하지 않아서, 다음 N23 차례의 변경 검사가 「N23이 잠긴 파일을 고쳤다」고 보고 차례를 실패시키고 두 파일을 되돌렸습니다(힌트 글과 학습 후보 L2가 지워짐). 이제 힌트는 자기 파일만 커밋하고, 실패한 노드의 작업 중 변경은 그대로 둡니다.
- **남은 빈 곳:** N15(두 번째 승인)에서 스펙·시나리오 모순이 보여도 Stage 0으로 되돌리는 경로가 없습니다(되돌림은 N11·N13·N14·N15로만). 이번에는 Stage 2에서 잡혔습니다. 검토 페이지에서 백틱 같은 Markdown 표시가 글자 그대로 보이는 작은 표시 문제도 남았습니다.
- **비용 관찰 (다시):** 오너 실행의 T6은 한 작업 세션을 스펙 모순, 되돌림, 다시 시작까지 이어 써서 N23 차례가 $1.0을 넘었습니다. 작업 세션을 이어 쓰는 비용은 조각 5의 개선 후보로 그대로 둡니다.

## 자기 검토

### 1차 검토에서 찾은 문제와 바꾼 점

- **채팅 승인은 창구 세션을 믿는 것:** 창구가 PO의 말을 잘못 옮기거나 작업 세션이 스스로 승인할 수 있습니다. 승인할 검토 ID와 PO의 말 원문을 요구하고, 작업 세션이 사람 명령을 못 쓰게 겹 셋(셸 훅, 세션 검사, 차례 뒤 원장 검사)을 두었습니다. 지금 셸 훅이 `4dd human`을 막지 않는다는 것도 찾았습니다.
- **PO가 본 것과 승인된 것이 다를 수 있음:** 페이지를 보낸 뒤 파일이 바뀌어도 승인되면 안 됩니다. 검토 해시로 묶었습니다.
- **PO는 설계를 판단하기 어려움:** `design.md`와 `tasks.md`를 PO 승인만으로 넘기면 확인하는 사람이 없습니다. N13·N14 관문에 리뷰 세션을 두고 그 결과를 N15 페이지에 보여 줍니다.
- **기다리는 동안 지휘 프로그램이 돌면 비용과 맥락이 샘:** 승인 대기에서 멈추고 끝나게 했습니다. 기다린 시간은 원장으로 잽니다.
- **세션 하나로 Stage 0·1을 다 돌리면** 차례마다 가격이 오르고, 다음 스테이지는 패킷만 믿는다는 원칙과도 어긋납니다. 스테이지마다 세션을 나눴습니다.

### 2차 검토에서 찾은 문제와 바꾼 점

- **승인이 세 번(N04, N11, N15):** N11 목표를 N15 페이지에 묶어 두 번으로 줄였습니다.
- **물을 것이 남은 채 승인되면** Stage 2에서 비싸게 돌아옵니다. 비어 있어야 승인되게 했습니다.
- **Stage 2에서 돌아온 N02가 요구사항을 더하면** 맡을 작업이 없어 N28에서 막힙니다. 돌아온 N02는 요구사항을 더하거나 빼지 않게 했습니다.
- **각본 PO의 승인이 사람 개입으로 잡히면** 지표가 틀립니다. `by: script`로 나눴습니다.
- **N04 되돌림의 PO 말이 N02에만 가면** 시나리오를 고치라는 말이 N03에 닿지 않습니다. 두 차례 모두에 힌트로 붙였습니다.
- **PO가 오너가 아닌 사람이면** 오너의 Claude 세션인 창구에 말할 길이 없습니다. 남은 위험에 적고 다음 후보(아티팩트 댓글)를 두었습니다.
- **품질 기준 점검:** 입력 경로(PO는 채팅, 개발자는 터미널, 같은 기록), 저장 형식(파일 형식, 원장 이벤트), 승인 단계(L0 추적 검사, L1 리뷰 세션, L2 PO), 에이전트가 읽는 길(`4dd context`가 ID로), 재사용 전 검증(검토 해시, 패킷, 기준 해시), 승격 경로(PO 의견 → 학습 후보 → 지시문 주의점), 첫 단계(구현 1단계)를 모두 적었습니다.

### 남은 위험

- 채팅 승인은 창구 세션이 PO의 말을 옮기는 것을 믿습니다. 검토 페이지의 승인 버튼(누가 눌렀는지를 아티팩트가 남김)이 다음 후보입니다.
- PO가 기술적인 질문을 받으면 답하기 어렵습니다. N02가 동작에 대한 질문만 하고 기술 결정은 N13으로 넘기게 했지만, 지시문이 지키는지는 돌려 봐야 압니다.
- 아티팩트 게시는 Claude만 하므로, Codex만 쓰는 곳에서는 검토 페이지 파일을 직접 열어 보는 길만 남습니다.
- 창구는 오너의 Claude 세션이라, 조각 2의 PO는 사실상 오너입니다. 다른 사람이 PO면 아티팩트를 공유하고 그 페이지의 댓글로 답을 받는 길이 후보입니다(창구가 댓글을 읽어 옮김).
- 새 기능이 기존 기능의 규칙을 바꾸면(잠긴 계정이 재설정으로 풀림) 기존 기능의 스펙도 고쳐야 할 수 있는데, 조각 2는 기능 하나의 스펙만 고칩니다. 이 경우 N02가 물을 것으로 올리는지 시험 스토리로 확인합니다.
- Stage 0·1의 작업 세션 차례(여섯 번 남짓)와 리뷰 두 번이 비용에 더해집니다. 실제로 재 보니 Stage 0·1은 Claude 표시 가격 약 $5.7이었고, 비용의 대부분은 Stage 2였습니다.
- 리뷰 세션이 얼마나 엄격한지는 도구마다 달랐습니다(Codex가 더 엄격). 실패 기준을 적어 맞췄지만, 새 노드의 리뷰 지시문도 같은 기준을 갖춰야 합니다.
