# 4DD 하네스 설계

> **상태 (2026-11-25):** 핵심 제안 5가지(설계 ①~⑤)와 노드 변경, 실패 원인 어휘, 횟수 제한에 이어, 사람 개입을 줄이며 서비스를 완성하고 스스로 개선하는 설계 ⑥·⑦, 하네스 실행까지 다루는 자기 개선용 온톨로지(설계 ③), 첫 구현 범위(MVP)까지 **모두 승인됐습니다.** 구현은 [첫 구현 조각 명세](harness-slice1.md)부터 시작해 첫 조각을 끝냈고, 다음은 [조각 2 명세](harness-slice2.md)입니다. 노드 변경과 되돌림 규칙은 [nodes.md](nodes.md)와 [workflow.md](workflow.md)에 반영했습니다. 아직 정하지 않은 것은 「열린 결정」에 있습니다. 목표는 논의를 거치면서 더 구체적으로 바뀌거나 진화할 수 있습니다.

## 목표

4DD 절차를 **하네스 엔지니어링**의 하네스로 만듭니다. 여기서 하네스는 에이전트 주변 환경을 말합니다. 컨텍스트(`AGENTS.md`, 문서), 도구(MCP, 명령), 가드레일(잠금, 훅), 피드백 루프(테스트, 관문, 리뷰), 상태를 설계해서 에이전트가 이 절차대로 앱을 만들거나 기능을 구현하게 합니다.

- **사람 개입은 최소로, 서비스는 완성까지:** 사람은 꼭 사람이 판단해야 하는 곳(맞는 제품인가, 기준을 바꾸나)에만 개입하고, 나머지는 에이전트와 기계 관문이 맡습니다. 스프린트 루프를 돌 때마다 서비스의 완성도가 올라가고, 완성 조건을 모두 채우면 멈춥니다 (2026-11-25 오너).
- **스스로 개선:** 루프마다 실패와 사람 개입에서 배워 하네스를 고칩니다. 다음 스프린트와 비슷한 다른 프로젝트에서는 더 적은 루프로, 더 적은 사람 개입으로 끝나야 합니다 (2026-11-25 오너).
- **도구 독립:** 같은 하네스가 Claude에서도, Codex에서도 돌아야 합니다. 두 도구가 작업을 주고받는 교대 방식이 아닙니다.
- **범용:** 주로 모바일 앱(React Native + Expo)을 만들고, 웹은 보조로 만듭니다. 백엔드 작업만 하거나 기능 하나만 구현하는 경우도 있습니다.
- **디자인도 에이전트가:** 디자인은 기본적으로 에이전트가 Figma MCP로 만들고, 사람은 일부만 맡습니다. Figma를 거쳐야 Figma 화면을 코드로 옮기는 기능(디자인 컨텍스트, Code Connect)을 쓸 수 있기 때문입니다.

사람 팀은 "Figma와 일치하나?" 같은 판단을 감으로 내리지만, 에이전트에게는 다음 세 가지가 필요합니다.

1. 기계로 확인할 수 있는 판단 기준
2. 스스로 승인하지 못하게 하는 구조
3. 무한 루프를 막는 횟수 제한

## 설계 ① 노드 정의 원본 (G1) — 승인

`4dd/nodes.yaml`을 노드 정의의 **유일한 원본**으로 둡니다. 사람이 보는 [nodes.md](nodes.md)와 Mermaid 맵은 이 파일에서 생성합니다. 하네스도 이 파일을 읽고 움직입니다.

```yaml
defaults:
  budget: 3                    # 판단 노드별 연속 실패 한도
  task_budget: 10              # 작업 하나의 되돌림 총합 한도
  flaky_retries: 1             # test_flaky 자동 재실행 (횟수에 안 셈)

N26F:
  stage: 2
  method: figma
  kind: decision
  actor: agent                 # agent | human | agent+human
  applies_to: [mobile, web]    # 이 노드가 켜지는 작업 유형
  reads: ["specs/{feature}/{feature}.feature", figma_frames]
  writes: ["src/**"]           # 이 노드에서 고쳐도 되는 경로
  gate:
    run: "{commands.visual} --scenario {scenario}"
    pass: exit_code == 0
    evidence: tests/visual/__diff__/
  on_fail:
    - when: ui_mismatch          # 실패 원인 어휘
      goto: N24
    - when: code_bug
      goto: N23
    - when: design_missing_state
      goto: N03W                 # 사람 승인 필요, 빠진 상태는 와이어부터 (동작까지 바뀌면 N03)
      then: N22                  # N04 승인 뒤 원래 작업으로 (스프린트 플래닝은 다시 안 함)
    - when: design_wrong
      goto: N03F                 # 사람 승인 필요, 프레임 자체가 틀렸을 때만 (동작까지 바뀌면 N03)
      then: N22
  budget: 5                    # 기본값 3 대신 5번 (화면 미세 조정이 많음)
```

## 설계 ② 상태 전달: 4층 구조 (G2) — 승인

| 층 | 무엇 | 형식 | 원본인가 |
|---|---|---|---|
| 산출물 | `spec.md`, `.feature`, 코드, Figma 파일 | 원래 형식 | 원본 |
| 원장 | 노드 진입·종료, 관문 결과, 훅 실행, 결정, 승인, 사람 개입 | `.4dd/events.jsonl` (추가만 함) | 원본 |

| 현재 상태 | 지금 어느 기능, 작업, 노드에 있나 | `.4dd/state.json` | 원장에서 다시 만들 수 있음 |

**원칙: 내용은 복사하지 않고 ID와 해시로 가리킵니다.** 사본이 생기면 원본과 어긋나고 토큰도 낭비됩니다. 다음 노드는 필요한 ID만 받아서 `4dd context <노드>` 명령으로 해당 파일과 섹션만 불러옵니다. 이 기록 덕분에 세션이 끊겨도 그 자리에서 다시 시작할 수 있고, 회고에서 쓸 데이터가 쌓입니다.

### 노드 인계 기록

원장의 한 줄입니다. `agent`에는 그 노드를 처리한 도구를 적습니다.

```json
{"type":"handoff","from":"N25","to":"N26","task":"T3","agent":"claude",
 "harness":"0.3.0","schema_version":1,"refs":["R2","S2","F:12-34@v7"],
 "outputs":[{"id":"src/auth/lock.ts","hash":"9f2c…"}],
 "decisions":["잠금 시간은 서버 시계 기준"],"open_questions":[],
 "commit":"a1b2c3d"}
```

커밋에도 `4DD-Node: N24`, `4DD-Refs: R2,S2` 같은 트레일러를 붙입니다. 그러면 코드 변경과 원장이 서로 연결됩니다.

### 스테이지 패킷

각 스테이지 경계에서 산출물을 고정하고, 다음 스테이지는 이 패킷만 믿고 출발합니다.

| 경계 | 고정하는 것 | 승인 |
|---|---|---|
| 0 → 1 | 승인된 R·S 목록, 프레임 ID와 Figma 버전, 해시 | N04 |
| 1 → 2 | `design.md`, `tasks.md` 해시, 스프린트 백로그 | N15 |
| 2 → 3 | 완료 작업, 관문 증거, 기준과 달라진 점 목록 | N29 |
| 3 → 4 | 분류된 피드백 (어느 S·F를 겨냥하는지) | N33 |
| 4 → 다음 | 승격된 개선 항목, 새 하네스 버전, 완성 조건 진행도 | N44 |

### 에이전트가 노드 하나를 처리하는 순서

1. `state.json`으로 현재 위치를 확인합니다.
2. `nodes.yaml`에서 그 노드의 정의를 찾습니다.
3. `4dd context <노드>`로 노드 지시문과 연결된 산출물만 읽습니다.
4. 작업하고 관문을 실행합니다.
5. 인계 기록과 증거를 원장에 남기고 다음 노드로 갑니다.

### 재사용 전 검증

노드가 산출물을 쓰기 전에, 현재 해시가 승인 당시 해시와 같은지 확인합니다. 다르면 "기준이 승인 없이 바뀐 것"이므로 진행을 멈추고 승인 노드로 돌아갑니다.

## 설계 ③ 자기 개선용 가벼운 온톨로지 (G3, G14, G20) — 승인

하네스가 프로젝트를 개발하며 스프린트 루프를 돌 때, **스스로 개선하는 데 쓸 기록을 셀 수 있게 만드는 층**입니다.

- **기록:** 원장에 남는 사실 한 줄입니다. 예: "N24가 T3에서 12분 걸렸고, 같은 훅에 두 번 막혔다."
- **온톨로지:** 그 사실에 붙이는 정해진 타입, 관계, 통제된 어휘입니다. 이름이 고정돼 있어야 스프린트, 하네스 버전, 프로젝트를 넘어 같은 종류끼리 세고 비교할 수 있습니다. 기록만 쌓으면 로그이고, 타입과 관계로 묶어야 질의할 수 있습니다.

무거운 온톨로지(OWL/RDF, 그래프 DB)가 아니라 ID, 관계, 어휘 정도로 시작합니다. 회고가 던지는 질문은 결국 "어느 노드가 어떤 지시문과 스킬로 돌았을 때 무슨 이유로 몇 번 실패했나" 같은 집계 질문입니다. 타입과 관계가 있으면 질의 한 번으로 답할 수 있습니다. 없으면 회고 때마다 에이전트가 로그 전체를 읽고 추측해야 해서 비싸고, 답도 매번 달라집니다.

온톨로지는 두 묶음을 다룹니다.

- **하네스 실행 (중심):** 하네스가 어떻게 돌았나. 어느 노드를 어떤 지시문과 스킬로 돌았고, 관문과 훅에서 어떻게 됐고, 사람이 어디서 개입했나.
- **개발 산출물 (보조):** 하네스가 그 프로젝트에서 만든 것. 실행 기록이 어느 요구사항, 어느 화면, 어느 작업에서 일어났는지 묶어 줍니다. N12 추적 검사에도 씁니다.

두 묶음은 작업에서 만납니다. 노드 실행은 작업에 속하고 작업은 요구사항을 구현하므로, "어떤 요구사항에서 어느 노드가 자주 실패하나"까지 이어서 물을 수 있습니다.

### 엔티티 타입

괄호 안은 스키마에 쓸 이름입니다.

**하네스 실행**

| 타입 | 뜻 | 어디서 자동으로 뽑나 |
|---|---|---|
| 노드 실행 (`NodeRun`) | 작업 하나에서 노드를 한 번 돈 것. 결과, 실패 원인, 토큰, 시간, 도구(Claude·Codex) | 원장의 노드 진입·종료와 인계 기록 |
| 관문 실행 기록 (`GateRun`) | 관문을 한 번 돌린 결과와 실패 원인 | `4dd gate` |
| 훅 실행 (`HookRun`) | 훅이 에이전트의 행동 하나를 막았나 통과시켰나, 어떤 검사였나 | `4dd check` (Claude 훅, git 훅, CI가 모두 이 명령을 부르므로 한 곳에서 남음) |
| 지시문 (`Instruction`) | 노드 지시문과 승격된 주의점 한 줄 | `nodes.yaml`, 지시문 파일의 해시 |
| 스킬 (`Skill`) | 하네스가 노드에 넘겨준 스킬 | 스킬 파일의 해시 |
| 훅 (`Hook`) | 규칙을 거는 입구 하나(Claude 훅, git 훅, CI 단계)와 그 검사 | 훅 설정 |
| 사람 개입 (`HumanIntervention`) | 그대로 승인, 고쳐서 승인, 힌트, 되돌림 | 원장의 사람 개입 기록 (설계 ⑦) |
| 하네스 버전 (`HarnessVersion`) | 지시문, 스킬, 관문, 훅을 묶은 버전 | 승격 기록 |
| 학습 항목 (`Learning`) | 개선 후보와 승격된 개선 | `.4dd/learnings.yaml` (설계 ⑥) |

**개발 산출물**

- 스토리 (`Story`)
- 요구사항 (`Requirement`, ID `R`)
- 시나리오 (`Scenario`, ID `S`)
- 프레임 (`Frame`, ID `F`)
- 컴포넌트 (`Component`, ID `C`)
- 작업 (`Task`, ID `T`)
- 테스트 (`Test`)
- 커밋 (`Commit`)
- 결정 (`Decision`)
- 피드백 (`Feedback`)
- 완성 조건 (`DoneCondition`, ID `P`)

### 관계

**하네스 실행**

| 주체 | 관계 | 대상 |
|---|---|---|
| 노드 실행 | 속한다 (`part_of`) | 작업 |
| 노드 실행 | 받았다 (`loaded`) | 지시문, 스킬 |
| 노드 실행 | 돌았다 (`ran_on`) | 하네스 버전 |
| 관문 실행 기록 | 평가한다 (`evaluates`) | 노드 실행 |
| 훅 실행 | 그 훅이 한 번 돈 것이다 (`run_of`) | 훅 |
| 훅 실행 | 막았다·통과시켰다 (`blocked`·`allowed`) | 노드 실행의 행동 하나 |
| 사람 개입 | 일어났다 (`intervened_in`) | 노드 실행 |
| 지시문, 스킬, 훅 | 들어 있다 (`included_in`) | 하네스 버전 |
| 학습 항목 | 나왔다 (`derived_from`) | 관문 실행 기록, 훅 실행, 사람 개입, 피드백 |
| 학습 항목 | 승격됐다 (`promoted_to`, 승인 필수) | 지시문, 스킬, 훅, `nodes.yaml`의 관문·노드 정의 |

**개발 산출물**

- 요구사항은 스토리에서 나온다 (`derived_from`)
- 시나리오는 요구사항을 검증한다 (`verifies`)
- 프레임은 시나리오의 한 상태를 그린다 (`depicts`)
- 컴포넌트는 프레임에 쓰인다 (`used_in`)
- 컴포넌트는 코드 컴포넌트에 연결된다 (`maps_to`, Code Connect)
- 작업은 요구사항을 구현한다 (`implements`)
- 테스트는 시나리오를 확인한다 (`checks`)
- 결정은 요구사항, 프레임, 기준값을 바꾼다 (`changes`, 승인 필수)
- 요구사항과 테스트는 완성 조건을 채운다 (`fulfills`)

### 추적 ID 붙이는 법

- `spec.md`의 요구사항에 `R1`, `R2` 같은 ID를 붙입니다.
- 시나리오에 `@R2` 태그를 답니다.
- `tasks.md`의 작업에 `T3 (R2)`처럼 요구사항 ID를 적습니다.
- 테스트도 같은 태그로 묶습니다. Maestro 플로우는 시나리오 ID를 파일 이름으로 씁니다(`S2.yaml`).

그래프는 손으로 관리하지 않습니다. 파일에 붙인 ID(`@R2` 태그, 프레임 주석, 커밋 트레일러, 플로우 파일 이름)와 원장에서 스캐너가 자동으로 뽑습니다. 하네스 실행 쪽 ID는 원장에 줄이 남을 때 기계가 붙입니다. ID가 빠지면 관문의 추적 검사가 잡아냅니다.

### 하네스 실행 기록

원장에 남는 줄의 예입니다. 내용은 남기지 않고 ID, 해시, 숫자만 남깁니다.

```json
{"type":"node_run","id":"NR88","node":"N24","task":"T3","agent":"claude","harness":"0.4.0",
 "loaded":[{"kind":"instruction","id":"N24","hash":"3f1a…"},
           {"kind":"skill","id":"figma-implement-design","hash":"9c2e…"}],
 "result":"fail","cause":"ui_mismatch","tokens":18400,"minutes":12}
{"type":"hook_run","id":"HR311","hook":"claude.pre_edit","check":"path_lock","run":"NR88",
 "target":".maestro/S2.yaml","result":"blocked","harness":"0.4.0"}
```

- **`loaded`에 적는 것:** 하네스가 `4dd context`로 넘겨준 지시문과 스킬입니다. 에이전트가 스스로 더 부른 스킬은 훅에서 잡습니다. Claude 훅과 Codex 훅 모두 비대화형 실행에서 도는 것을 첫 구현 조각에서 확인했습니다(Codex는 사용자 설정에 넣고 사람이 한 번 신뢰한 뒤).
- **누가 쓰나:** 기계만 씁니다. 에이전트의 자기 보고는 받지 않습니다.
- **어디에 쓰나:** 학습 항목은 이 기록의 ID를 근거로 적습니다(설계 ⑥의 `evidence`).

### 반복 실수와 비효율 찾기

회고(N42, N43)에서 기계가 아래 질의를 돌리고, 결과를 개선 지표 페이지에 붙입니다.

| 질문 | 찾아내는 것 |
|---|---|
| 같은 노드가 같은 훅에 반복해서 막히나? | 반복 실수: 지시문이 잠긴 경로를 알려 주지 않음 |
| 같은 실패 원인이 같은 노드나 같은 종류의 요구사항에서 반복되나? | 반복 실수 |
| 두 노드 사이를 몇 번 오가나(N26F ↔ N24)? 토큰과 시간을 가장 많이 쓰는 노드는? | 비효율 |
| 받아도 첫 통과율이 그대로인 스킬과 지시문 줄은? | 효과 없는 규칙 (정리 후보) |
| 규칙을 올린 하네스 버전 전후로 그 실패 원인이 줄었나? | 규칙 효과 |
| 사람 개입이 어느 노드, 어느 원인에 몰리나? | 다음에 줄일 사람 개입 |
| 같은 노드에서 Claude와 Codex의 결과가 다른가? | 도구별 차이 |

- 찾은 것은 바로 고치지 않습니다. 설계 ⑥의 후보가 되어 시험 세트를 거친 뒤에만 규칙이 됩니다.
- 함께 나타났다고 원인은 아닙니다. 예를 들어 스킬을 받은 노드가 원래 쉬운 노드였을 수 있습니다. 그래서 그래프는 후보를 찾는 데만 쓰고, 효과는 시험 세트로 판정합니다.
- 훅은 한 번도 막지 않았더라도 정리 후보로 두지 않습니다. 안전장치를 빼는 것은 기준을 푸는 변경이라 사람이 정합니다.
- 타입과 관계를 더하는 것도 실패 원인 어휘처럼 회고에서 승인받습니다.

### 실패 원인 통제 어휘 — 승인

자유 텍스트로 쓰면 집계할 수 없으므로 정해진 단어 10개만 씁니다(`code_bug`, `ui_mismatch`, `spec_ambiguous`, `spec_missing_state`, `design_missing_state`, `design_wrong`, `arch_wrong`, `test_flaky`, `env`, `budget_exceeded`). 처음 8개로 시작했고, `design_wrong`은 2026-11-23에, `arch_wrong`은 2026-11-24에 오너가 승인했습니다. 어휘를 추가하려면 회고에서 승인을 거칩니다.

어휘마다의 뜻, 예, 돌아갈 곳, 고친 뒤 갈 곳, 승인 주체는 [workflow.md](workflow.md#실패-원인과-횟수-제한)에 한 번만 적어 둡니다. 같은 표를 여러 문서에 두면 어긋나기 때문입니다. 하네스를 구현할 때는 이 표를 `nodes.yaml`의 `on_fail`로 옮기고(돌아갈 곳은 `goto`, 고친 뒤 갈 곳은 `then`), 그때부터는 `nodes.yaml`이 원본이 됩니다.

### 회고 진화 루프

회고가 하네스를 고치는 루프는 아래 「설계 ⑥ 스스로 개선하는 루프」로 넓혔습니다. 근거로 삼는 데이터가 위의 원장, 그래프, 실패 원인 어휘입니다.

## 설계 ④ 에이전트가 하는 디자인 (G8~G11) — 승인

### 조사로 확인한 사실 (2026-11-13)

- **흐름:** Figma가 디자인을 완성된 코드로 뽑아 주는 방식이 아닙니다. Figma MCP가 디자인 정보(구조, 변수, 스크린샷, 연결된 컴포넌트)를 넘기면, 에이전트가 그걸 참고해 우리 코드베이스에 맞게 구현합니다. Figma와 OpenAI 모두 MCP 출력(기본 React + Tailwind)을 "구조 참고용"으로 다루라고 안내합니다.
- **공식 스킬:** Claude와 Codex 양쪽에서 같은 스킬을 쓸 수 있습니다.
  - 그리기: `figma-generate-library`(디자인 시스템), `figma-generate-design`, `figma-use`(화면)
  - 구현: `figma-implement-design`
  - 디자인 규칙 스킬은 `CLAUDE.md`와 `AGENTS.md` 양쪽 형식을 지원합니다.
- **Professional 요금제 조건:**
  - Code Connect(Figma 안에 부품과 코드 파일을 잇는 기능)는 **쓸 수 없습니다.** 처음에는 된다고 적었는데, 조각 3 실제 실행에서 Figma가 「Organization·Enterprise 요금제의 라이브러리에서만 된다」며 거부했습니다(2026-11-27). 오너 결정으로 요금제는 그대로 두고, 같은 짝을 저장소 파일(`design/code-connect.json`)로 둡니다. 구현 세션은 그 파일로 부품을 찾습니다.
  - MCP 읽기 호출은 하루 200회, 분당 10회로 제한됩니다. 쓰기 도구는 이 제한에서 빠집니다.
  - 캔버스 쓰기(`use_figma`)도 쓸 수 있습니다. 베타 기간에는 무료입니다.
- **React Native:** Code Connect가 공식 지원합니다. MCP 기본 출력은 웹용이므로, Code Connect 라벨을 React Native로 맞추고 "웹 코드는 구조 참고용이고 React Native로 옮겨 쓴다"는 규칙을 지시문에 넣습니다.

| N00F 디자인 시스템 준비 (신규, 프로젝트당 1회) | Figma 변수(색, 간격, 글꼴, 모서리)와 컴포넌트를 만들고, Code Connect로 React Native 컴포넌트에 연결합니다. 이게 없으면 Figma → 코드 결과가 날것의 덩어리가 됩니다. 관문: 모든 컴포넌트가 Code Connect에 연결됐는지, Figma 변수와 코드 테마 파일의 값이 같은지. |

### 화면 비교 기준 (N26F) — 결정

- 판정은 "디자인과 구현의 차이 비율"로 합니다. **기본값 5%**이고 설정으로 바꿀 수 있습니다.
- 업계 표준 수치는 없습니다. 참고로 Maestro `assertScreenshot`의 기본값은 95% 일치(5% 허용), Playwright는 기본 0 허용입니다. Figma와 실제 화면 비교는 폰트 렌더링과 안티앨리어싱 차이 때문에 맞게 구현해도 픽셀이 완전히 같지 않습니다.
- Maestro에는 `thresholdPercentage = 100 - tolerance_percent`로 넘깁니다. Maestro는 이 값에 변수를 받습니다.
- 정확도를 위해 기기와 해상도를 고정하고, 상태 표시줄처럼 매번 바뀌는 영역은 비교에서 뺍니다(`cropOn`).
- **기준값은 사람이 정하는 기준입니다.** 에이전트는 바꿀 수 없게 잠그고, 바꾸려면 결정 기록과 승인을 거칩니다. 에이전트가 기준을 느슨하게 바꿔 통과시키는 것을 막기 위해서입니다.

```yaml
# 4dd.config.yaml 일부
visual:
  tolerance_percent: 5        # 디자인과 구현 차이 허용 비율
  overrides:                  # 시나리오별 예외 (선택)
    S7: 8                     # 예: 애니메이션이 있는 화면
  device: android_pixel_7_api_34
  ignore: [status_bar]
```

### 순환 문제 (G10)

같은 세션이 그리고 구현하고 비교까지 하면 Figma 관문이 독립적인 검사가 되지 못합니다.

- **세션 분리:** 디자인 세션, 구현 세션, 리뷰 세션을 나눕니다. 같은 도구여도 됩니다.
- **버전 고정:** 구현 노드(N2x)에서는 고정된 버전의 Figma 프레임에 쓸 수 없게 잠급니다. 디자인을 바꾸려면 N03F로 되돌아가 결정 기록을 남기고 승인을 받아야 합니다.

### 되돌림과 횟수 제한 (G5)

- 실패 원인 어휘로 갈 곳을 정합니다 ([workflow.md](workflow.md#실패-원인과-횟수-제한) 참고).
- N26F 실패는 원인으로 가릅니다. 화면 차이(`ui_mismatch`)면 N24로 바로 갑니다. 실패한 화면 비교가 이미 Red 역할을 하므로, 화면을 조금 고치려고 단위 테스트부터 쓸 필요가 없습니다. 로직 오류(`code_bug`)면 N23으로 갑니다. 프레임 자체가 틀려서 프레임대로는 맞출 수 없을 때만 `design_wrong`으로 기록하고, 사람이 승인하면 N03F로 갑니다.
- N27 실패도 같은 방식입니다. 기본은 설계대로 코드를 고치고(`code_bug`, N23), 설계 자체가 틀렸을 때만 `arch_wrong`으로 기록해 사람이 승인하면 N13으로 갑니다.
- 개발 중에 Stage 0으로 돌아간 작업은 N04에서 다시 승인받으면 원래 작업의 N22로 돌아옵니다. 스프린트 플래닝은 다시 하지 않습니다. 화면을 고치다 동작까지 바뀌면 N03(시나리오)부터 고칩니다.
- `test_flaky`로 N22에서 테스트를 고친 뒤에는 코드가 그대로이므로 N26으로 바로 갑니다.
- 횟수 제한: 판단 노드별 기본 3회, N26F는 5회, 작업 하나 전체는 10회입니다. `test_flaky`는 자동으로 한 번 재실행하고, 그건 횟수에 넣지 않습니다. 넘으면 멈추고 실패 기록 요약과 함께 사람을 부릅니다.
- "코드 문제"는 에이전트가 직접 되돌리고, "기준(스펙·디자인·기준값) 문제"는 에이전트가 판단만 한 뒤 사람이 승인해야 되돌립니다.

### 쓰기 잠금 (G6)

- 노드마다 수정할 수 있는 경로(`writes`)를 정합니다. 예를 들어 N23~N25에서는 `.feature`, Maestro 플로우, `spec.md`, `4dd.config.yaml`, 고정된 버전의 Figma 프레임을 고칠 수 없습니다.
- N28 관문에서 추가로 검사합니다: 테스트 수가 줄지 않았나, 테스트를 건너뛰는 표시가 새로 생기지 않았나, 기준선 이미지나 기준값이 무단으로 바뀌지 않았나.

### 강제 규칙을 거는 곳 — 결정

규칙은 `nodes.yaml`과 `4dd` 명령 **한 곳에만** 정의합니다. 나머지는 `4dd` 명령을 부르는 입구일 뿐입니다. 그래야 도구가 달라도 같은 규칙이 적용되고, 규칙이 여러 곳에서 어긋나지 않습니다.

| 층 | 언제 걸리나 | 하는 일 | 적용 도구 |
|---|---|---|---|
| ④ Claude 전용 훅 | 파일을 고치기 **직전** (가장 빠름) | 편집 전 `4dd check path <파일>`로 잠긴 경로를 막음, 세션 시작 시 `4dd context`를 넣어 줌, 세션 끝에 인계 기록이 남았는지 확인 | Claude |
| ① `4dd` 명령 | 에이전트가 직접 부를 때 | `4dd context`, `4dd gate <노드>`, `4dd check`, `4dd advance` | 공통 |
| ② git 훅 | 커밋할 때 | pre-commit에서 잠금 검사와 추적 검사, commit-msg에서 트레일러 확인 | 공통 |
| ③ CI | PR을 올릴 때 (마지막 관문) | 모든 관문을 다시 실행. git 훅은 건너뛸 수 있어도 CI는 못 건너뜀 | 공통 |

Codex는 ①~③으로 같은 규칙을 적용받습니다. Codex에도 훅 기능이 있다는 것을 확인했습니다(2026-11-25). 파일 수정(`apply_patch`)과 셸 명령 전에 걸리고, Claude 훅처럼 종료 코드 2로 막습니다. 그래서 ④에 같은 `4dd check`를 겁니다. 다만 Codex는 사람이 한 번 신뢰한 훅만 돌리므로, 첫 구현 조각에서 훅이 켜져 있는지 원장으로 확인합니다.

### 승인 3층 (G7, G12)

| 단계 | 누가 | 언제 |
|---|---|---|
| L0 기계 관문 | 하네스 | 매 반복마다, N12 준비 확인 |
| L1 별도 리뷰 | 다른 에이전트 세션 (같은 도구여도 됨) | 작업과 디자인이 끝날 때, 머지(CI와 함께), 규칙을 조이는 학습 항목 승격 |

### 비개발자 입력 경로 (G12)

- **PO:** Git을 쓰지 않아도 됩니다. 채팅, Notion, 이슈 어디든 평범한 말로 스토리를 적으면, 에이전트가 `spec.md`와 `.feature` 초안으로 바꾸고 렌더링된 검토 페이지를 만듭니다. PO는 그 페이지에서 승인하거나 의견을 남깁니다.
- **디자이너 (일부 참여 시):** Figma에서 에이전트가 만든 프레임을 보고 고치거나 승인합니다.

**작업 유형**에 따라 켜지는 D가 다릅니다. 노드의 `applies_to`로 정합니다.

## 설계 ⑥ 스스로 개선하는 루프 (G14, G18, G19) — 승인 (2026-11-25)

루프마다 실패와 사람 개입에서 배우고, 바꾼 것이 정말 나아졌는지 시험한 뒤에만 규칙으로 올립니다. 다른 하네스와 연구에서 확인한 방식을 4DD에 맞췄습니다(아래 「출처」).

```
기록 ─▶ 후보 ─▶ 다시 돌려 보기 ─▶ 승격 ─▶ 정리 ─▶ 다른 프로젝트로 옮기기
```

### 개선 단계

| 단계 | 언제 | 누가 | 하는 일 |
|---|---|---|---|
| 기록 | Stage 2 내내 | 기계 | 노드 실행, 관문 결과, 훅 실행, 실패 원인, 사람 개입, 토큰과 시간을 원장에 남김(설계 ③). 에이전트의 자기 보고는 받지 않음 |
| 후보 | 작업 중 · N42·N43 | 에이전트 | 횟수 초과 때 사람이 준 힌트는 바로 후보로. 회고에서는 설계 ③의 질의로 실패와 성공 둘 다에서 후보를 뽑음. 후보마다 근거 ID, 바꾸는 것 하나, 잴 지표 하나 |
| 다시 돌려 보기 | 하네스를 바꿀 때 | 기계 | 시험 세트를 지금 버전과 후보 버전으로 각각 돌려 비교. 작은 세트를 통과하면 큰 세트 |
| 승격 | N44 | 등급에 따라 | 아래 「승격 등급」대로 승인하고 하네스 버전을 올림 |
| 정리 | 수시 | 에이전트, 사람 확인 | 근거가 사라졌거나 시험에서 차이가 없는 규칙은 퇴역. 지시문 크기를 예산 안으로 유지 |
| 옮기기 | 프로젝트 끝 | 사람 | 일반적인 학습을 공통 층으로 올림. 새 프로젝트는 시작할 때 공통 층을 불러옴 |

### 개선 지표

| 지표 | 뜻 | 좋아지는 쪽 |
|---|---|---|
| 작업당 사람 개입 수 | 사람이 승인, 힌트, 수정으로 손댄 횟수 | 줄어듦 (가장 중요) |
| 첫 통과율 | 판단 노드를 첫 번에 통과한 비율 | 늘어남 |
| 작업당 되돌림 수 | 실패 원인별 되돌림 횟수 | 줄어듦 |
| 기능당 스프린트 수 | 기능 하나를 끝내는 데 든 스프린트 | 줄어듦 |
| 작업당 토큰과 시간 | 작업 하나에 든 비용 | 줄어듦 |

빨라졌는지만 보면 지표를 맞추려고 품질을 버릴 수 있습니다. 그래서 짝 지표로 **리뷰(N31~N33)에서 나온 버그 수**를 함께 보고, 이 숫자가 늘면 다른 지표가 좋아져도 개선으로 치지 않습니다.

### 승격 등급

| 변경 | 승인 | 조건 |
|---|---|---|
| 규칙을 조이는 변경 (지시문에 주의점 추가, 관문이나 검사 추가) | L1 별도 리뷰 세션 | 시험 세트에서 나빠지지 않고 지표가 나아짐, 지시문 크기 예산 안 |
| 기준을 푸는 변경 (허용 비율, 횟수 제한, 노드 삭제, 관문 완화) | L2 사람 | 결정 기록과 시험 결과를 함께 봄 |
| 에이전트가 만든 스킬 | L1, 시험 필수 | 스킬이 있을 때와 없을 때를 시험 세트로 비교해 나아질 때만 |
| 공통 층 승격 | L2 사람 | 아래 「공통 층과 프로젝트 전용 층」 |

같은 교정이 두 번 넘게 나오면 한 단계 올립니다: 지시문 한 줄 → 스킬 → 관문이나 훅. 지시문으로 거듭 말해도 지켜지지 않는 규칙은 기계가 막아야 합니다.

### 학습 항목 저장

학습 항목은 `.4dd/learnings.yaml`에 ID가 붙은 작은 항목으로 쌓습니다. 통째로 다시 쓰지 않고 항목을 더하거나 고치거나 퇴역시키기만 합니다. 통째로 다시 쓰면 세부가 사라지기 때문입니다.

```yaml
- id: L12
  scope: project              # project | common
  kind: instruction           # instruction | skill | gate | hook | node
  change: "N24 지시문: 잠금 시간은 서버 시계로 계산한다"
  evidence: [G341, G352, F:12-34@v7]   # 관문 실행 기록, 피드백, 코드 위치
  metric: spec_ambiguous_per_task
  status: promoted            # candidate | trial | promoted | retired
  harness: 0.4.0
  verified_at: 2026-11-25
```

- **다시 쓰기 직전 검증:** 근거로 적은 파일이나 코드 위치가 아직 있는지 확인합니다. 사라졌으면 쓰지 않고 정리 대상으로 넘깁니다.
- **에이전트가 읽는 길:** 개발 중인 에이전트는 이 파일을 읽지 않습니다. 승격된 규칙만 `nodes.yaml`, 지시문, 스킬을 거쳐 `4dd context`로 들어옵니다. 승인되지 않은 교훈이 행동에 섞이지 않게 하기 위해서입니다.
- **사람이 보는 길:** 회고 때 후보를 근거와 시험 결과와 함께 검토 페이지에 모읍니다. PO와 디자이너는 Git 없이 그 페이지에서 묶어서 승인하고, 개발자는 PR로도 볼 수 있습니다.

### 시험 세트

하네스를 바꿨을 때 스프린트 전후만 비교하면 기능마다 난이도가 달라 공정하지 않습니다. 그래서 끝낸 작업을 `.4dd/replay/`에 모아 둡니다. 작업마다 시작 커밋과 기대하는 관문 결과를 적고, 같은 작업을 지금 버전과 바뀐 버전으로 돌려 비교합니다.

- 에뮬레이터 빌드와 인수 테스트는 느리므로, 하네스를 바꿀 때만 돌리고 작은 세트부터 돌립니다.
- 에이전트는 시험 세트, 관문 정의, 원장을 고칠 수 없습니다. 평가 장치를 고쳐서 통과하는 것을 막기 위해서입니다.

### 공통 층과 프로젝트 전용 층

| 층 | 어디 | 무엇 | 올리는 조건 |
|---|---|---|---|
| 프로젝트 전용 | 프로젝트의 `.4dd/`와 `nodes.yaml` | 이 서비스와 코드에만 맞는 학습 | 승격 등급대로 |
| 공통 (시험 중) | 하네스 자체의 새 버전 | 다른 프로젝트에도 맞을 것 같지만 근거가 프로젝트 하나뿐인 학습 | 사람 승인 |
| 공통 | 하네스 자체의 새 버전 | 두 개 이상의 프로젝트에서 효과가 확인된 학습 | 사람 승인 |

새 프로젝트는 시작할 때(N00) 공통 층을 불러옵니다. "시험 중" 항목은 그 프로젝트의 시험 세트에서 다시 확인하고, 효과가 없으면 공통 층에서 뺍니다.

- N32에서 진행도를 재고, 모두 채우면 N44에서 PO가 승인하고 프로젝트를 마칩니다. 규칙은 [workflow.md](workflow.md#서비스-완성)에 한 번만 적습니다.

### 사람 승인 줄이기

| 지점 | 전 | 후 |
|---|---|---|
| N12 준비 확인 | 사람(팀 전체) | 추적 검사(L0): 스펙·시나리오·프레임 ID가 모두 있고 N04 승인 당시 해시와 같은지. 사람은 표본 |
| 머지 | 사람 | CI와 별도 리뷰 세션(L1). 사람은 표본 |
| N11 목표, N15 백로그 확정 | 사람 회의 | 에이전트가 완성 조건과 지난 처리량으로 초안, 사람은 승인 |
| N2D 데일리 스크럼 | 매일 15분 회의 | 하네스가 원장으로 만드는 진행 요약 |
| 기준 변경 (스펙·디자인·기준값·횟수 제한·완성 조건) | 사람 | 그대로 늘 사람 |

- 표본 비율은 **사람이 고친 비율**로 조절합니다. 사람이 표본에서 고친 것이 적으면 비율을 낮추고, 많으면 높입니다. 승인 비율이 아니라 고친 비율로 재는 이유는, 사람이 대충 승인한 것까지 실적으로 잡히지 않게 하기 위해서입니다.
- 기준 변경은 표본 비율을 0으로 낮추지 않습니다.

### 사람 개입 기록

사람이 개입할 때마다 원장에 한 줄을 남깁니다. 개선 지표의 "작업당 사람 개입 수"가 이 기록에서 나옵니다.

```json
{"type":"human","node":"N26F","task":"T3","kind":"hint",
 "reason":"budget_exceeded","minutes":6,"harness":"0.4.0"}
```

`kind`는 `approve`(그대로 승인), `edit`(고쳐서 승인), `hint`(힌트를 주고 다시 시도), `reject`(되돌림) 중 하나입니다.

6. 조각 3(2026-11-26 명세 초안): 화면 기능을 Figma 디자인부터 Android·웹 구현과 화면 비교까지 갑니다. 오너가 시험 대상(로그인·회원 가입 앱 화면), Figma 위치(「패스투웨이의 팀」), 웹(같은 앱을 Expo 웹으로), 디자인 시스템 확인(리뷰 세션, 오너는 첫 N04에서 함께)을 정했고, 명세의 제안 일곱 가지도 그대로 승인했습니다(2026-11-27, [harness-slice3.md](harness-slice3.md)). 두 도구의 각본 PO 실행, 오너가 PO인 실제 실행(「회원 가입 화면」, 2026-11-28), 백엔드 스토리 실행으로 완료 기준을 확인했고, 그 실행들에서 찾은 하네스 문제 열세 가지를 고쳤습니다. 다 고친 하네스로 Codex는 화면 기능을, Claude는 백엔드 스토리를 개발자 개입 없이 끝냈습니다.
7. 조각 3~5(2026-11-25 오너 지시): 조각을 모두 끝낼 때까지, 완성도를 높이는 쪽으로 골라 이어서 진행합니다. 각 조각의 명세는 앞 조각이 끝난 뒤에 쓰고, 바뀐 것은 아티팩트에 반영합니다.

## 자기 검토

### 1차 검토에서 찾은 문제와 바꾼 점

- 온톨로지를 RDF와 그래프 DB로 잡았는데, 운영 비용이 크고 에이전트가 직접 쓰기 어렵습니다. 파일 안 ID에서 자동으로 뽑는 인덱스로 줄였습니다.
- 인계 기록에 산출물 내용을 담으려 했는데, 토큰이 낭비되고 사본이 어긋납니다. ID와 해시로 가리키는 방식으로 바꿨습니다.
- 같은 세션이 디자인, 구현, 비교를 모두 하면 독립성이 사라집니다. 세션 분리와 버전 고정을 추가했습니다.
- 디자인 시스템 없이 바로 화면부터 그리면 Figma → 코드 품질이 낮습니다. N00F를 제안했습니다.

### 2차 검토에서 찾은 문제와 바꾼 점

- 진화 루프가 개선 효과를 측정할 수 없었습니다. 원장에 하네스 버전을 기록해 전후를 비교하게 했습니다.
- 실패 원인을 자유 텍스트로 쓰면 집계할 수 없습니다. 통제 어휘로 바꿨습니다.
- 목표가 진화하므로 스키마도 바뀔 것입니다. 원장과 그래프에 `schema_version`을 넣었습니다.

### 3차 검토 (결정 사항 반영 후)

- "Claude ↔ Codex 교대"를 전제로 쓴 부분이 있었습니다. 목표는 도구 독립이므로, 교차 리뷰를 "별도 리뷰 세션"으로 바꾸고 인계 실험을 지웠습니다.
- 기준값을 설정으로 바꿀 수 있게 하면 에이전트가 기준을 느슨하게 고쳐 통과시킬 수 있습니다. 기준값 파일을 쓰기 잠금 대상에 넣고, 바꿀 때는 결정 기록과 승인을 거치게 했습니다.
- 규칙을 Claude 훅, git 훅, CI에 따로 쓰면 서로 어긋납니다. 규칙은 `4dd` 명령 한 곳에 두고 나머지는 입구로만 쓰게 했습니다.
- 백엔드 작업에는 Figma 노드가 필요 없습니다. 작업 유형별로 켜지는 노드를 정하게 했습니다.

### 4차 검토 (승인 대기 항목 확정 때)

- N26F 실패를 무조건 N24로 보내면 화면이 틀린 원인이 로직일 때 단위 테스트 없이 넘어갑니다. 실패 원인으로 갈라서 `code_bug`는 N23으로 보내게 했습니다.
- 판단 노드별 횟수만으로는 판단 노드 사이를 오가며 맴도는 경우를 못 잡습니다. 작업 하나 전체 상한(10회)을 추가했습니다.
- 실패 원인 표를 여러 문서에 두면 어긋납니다. [workflow.md](workflow.md#실패-원인과-횟수-제한) 한 곳에 두고 나머지는 그곳을 가리키게 했습니다.

### 5차 검토 (설계 ⑥·⑦, 2026-11-25)

- 규칙을 조이는 변경을 바로 자동 승격하려 했는데, 컨텍스트 파일과 지시문을 늘리면 오히려 성공률이 떨어지고 비용이 는다는 연구가 있습니다. 시험 세트 통과와 지시문 크기 예산을 조건으로 걸었습니다.
- 승인 비율이 높으면 사람 검토를 줄이려 했는데, 사람이 대충 승인한 것까지 실적으로 잡힙니다. 사람이 고친 비율로 재고, 기준 변경은 표본 비율을 0으로 내리지 않게 했습니다.
- 에이전트가 스스로 만든 스킬은 평균 효과가 없었다는 연구가 있습니다. 스킬은 시험 세트에서 있을 때와 없을 때를 비교해 나아질 때만 승격합니다.
- 자기 코드를 고치는 에이전트가 평가 장치를 우회한 사례가 있습니다. 시험 세트, 관문 정의, 원장은 에이전트가 고칠 수 없게 했고, 원장은 기계만 씁니다.
- 공통 층에 "프로젝트 두 개 이상" 조건만 두면 처음에는 늘 비어 있습니다. "시험 중" 단계를 두어 다음 프로젝트에서 확인하게 했습니다.
- 시험 세트는 에뮬레이터 때문에 느립니다. 하네스를 바꿀 때만, 작은 세트부터 돌립니다.

### 6차 검토 (자기 개선용 온톨로지, 2026-11-25)

- 온톨로지가 개발 산출물만 다뤄서, 하네스가 어떻게 돌았는지는 셀 수 없었습니다. 노드 실행, 훅 실행, 지시문, 스킬, 훅, 사람 개입, 하네스 버전을 타입으로 더하고 중심에 두었습니다.
- 무엇이든 남기면 원장이 커지고 토큰이 늘어납니다. 내용은 남기지 않고 ID, 해시, 숫자만 남깁니다.
- 에이전트가 어떤 스킬을 썼는지 알아내는 방법이 도구마다 다릅니다. 하네스가 `4dd context`로 넘겨준 것을 기록하고, 에이전트가 스스로 더 부른 것은 훅이 있는 도구에서만 더합니다.
- 함께 나타났다고 원인은 아닙니다. 그래프는 후보를 찾는 데만 쓰고, 효과는 시험 세트로 판정합니다.
- 한 번도 막지 않은 훅을 정리 후보로 두려 했는데, 안전장치를 빼는 것은 기준을 푸는 변경입니다. 훅은 정리 질의에서 빼고, 정리 후보는 효과 없는 스킬과 지시문 줄로 한정했습니다.
- 타입이 마음대로 늘지 않게, 타입과 관계를 더하는 것도 회고에서 승인받습니다.

### 남은 위험

- Figma 쓰기 베타의 안정성과 요금, 도구 이름의 변동
- Professional의 하루 200회 읽기 한도: 화면이 많은 기능에서는 부족할 수 있습니다.
- LLM이 그린 디자인이 무난하고 평범해지는 경향: 디자인 시스템과 참고 화면으로만 일부 보완할 수 있습니다.
- N27의 의미적 일치는 끝까지 완전 자동화가 어렵습니다.
- 쓰기 잠금도 설정 파일로 테스트를 제외하는 식으로 우회할 수 있습니다. 테스트 수 검사와 CI로 일부만 막습니다.
- iOS는 Mac이 생길 때까지 검증되지 않습니다.
- 초기에는 기록이 적어서 개선 지표와 온톨로지 질의 결과가 우연에 흔들립니다. 첫 몇 스프린트는 기준선으로만 씁니다.
- Codex의 비대화형 실행에서 훅이 어떻게 동작하는지는 공식 문서에 없습니다. 편집 막기와 세션 시작 기록은 실제로 확인했지만(2026-11-25), 셸 명령 막기는 아직 확인하지 않았습니다.
- 시험 세트를 만들고 유지하는 비용이 듭니다.
- 사람 개입을 줄이는 것과 안전장치 사이에는 긴장이 있습니다. 표본 비율을 어디까지 낮출지는 실적을 보며 오너가 정합니다.
- 스프린트(1~4주)는 사람의 리듬입니다. 에이전트는 그 안에서 작업 루프를 여러 번 도는 것으로 보았는데, 이 해석은 확인이 필요합니다.
