# 4DD 하네스 설계 (초안)

> **상태: 제안 초안 (2026-11-13).** 아직 확정된 절차가 아닙니다. 여기서 제안한 노드 변경(N00F 신설, N03F 두 단계 분리, 되돌림 경로 변경)은 [nodes.md](nodes.md)와 [workflow.md](workflow.md)에 반영하지 않았습니다. 목표는 논의를 거치면서 더 구체적으로 바뀌거나 진화할 수 있습니다.

## 목표

4DD 절차를 **하네스**로 만들어 Claude나 Codex 같은 코딩 에이전트가 이 절차대로 앱을 만들거나 기능을 구현하게 합니다. 디자인도 기본적으로 에이전트가 **Figma MCP**로 만들고, 사람은 일부만 맡습니다. Figma를 거쳐야 Figma 화면을 코드로 옮기는 기능(디자인 컨텍스트, Code Connect)을 쓸 수 있기 때문입니다.

사람 팀은 "Figma와 일치하나?" 같은 판단을 감으로 내리지만, 에이전트에게는 다음 세 가지가 필요합니다.

1. 기계로 확인할 수 있는 판단 기준
2. 스스로 승인하지 못하게 하는 구조
3. 무한 루프를 막는 횟수 제한

## 설계 ① 노드 정의 원본 (G1)

`4dd/nodes.yaml`을 노드 정의의 **유일한 원본**으로 둡니다. 사람이 보는 [nodes.md](nodes.md)와 Mermaid 맵은 이 파일에서 생성합니다. 하네스도 이 파일을 읽고 움직입니다.

```yaml
N26F:
  stage: 2
  method: figma
  kind: decision
  actor: agent                 # agent | human | agent+human
  reads: ["specs/{feature}/{feature}.feature", figma_frames]
  writes: ["src/**"]           # 이 노드에서 고쳐도 되는 경로
  gate:
    run: "{commands.visual} --grep @{scenario}"
    pass: exit_code == 0
    evidence: tests/visual/__diff__/
  on_fail:
    - when: ui_mismatch          # 실패 원인 어휘
      goto: N24
    - when: design_missing_state
      goto: N03F                 # 사람 승인 필요
  budget: 3                    # 3번 실패하면 사람 호출
```

## 설계 ② 상태 전달: 4층 구조 (G2)

| 층 | 무엇 | 형식 | 원본인가 |
|---|---|---|---|
| 산출물 | `spec.md`, `.feature`, 코드, Figma 파일 | 원래 형식 | 원본 |
| 원장 | 노드 진입·종료, 관문 결과, 결정, 승인 | `.4dd/events.jsonl` (추가만 함) | 원본 |
| 그래프 | 엔티티와 관계 (온톨로지) | `.4dd/graph.jsonl` | 산출물과 원장에서 자동 추출 |
| 현재 상태 | 지금 어느 기능, 작업, 노드에 있나 | `.4dd/state.json` | 원장에서 다시 만들 수 있음 |

**원칙: 내용은 복사하지 않고 ID와 해시로 가리킵니다.** 사본이 생기면 원본과 어긋나고 토큰도 낭비됩니다. 다음 노드는 필요한 ID만 받아서 `4dd context <노드>` 명령으로 해당 파일과 섹션만 불러옵니다.

### 노드 인계 기록

원장의 한 줄입니다.

```json
{"type":"handoff","from":"N25","to":"N26","task":"T3","agent":"claude",
 "harness":"0.3.0","schema_version":1,"refs":["R2","S2","F:12-34@v7"],
 "outputs":[{"id":"src/auth/lock.ts","hash":"9f2c…"}],
 "decisions":["잠금 시간은 서버 시계 기준"],"open_questions":[],
 "commit":"a1b2c3d"}
```

커밋에도 `4DD-Node: N24`, `4DD-Refs: R2,S2` 같은 트레일러를 붙입니다. 그러면 코드 변경과 원장이 서로 연결됩니다.

### 스테이지 패킷

각 스테이지 경계에서 산출물을 고정하고, 다음 스테이지는 이 패킷만 믿고 출발합니다.

| 경계 | 고정하는 것 | 승인 |
|---|---|---|
| 0 → 1 | 승인된 R·S 목록, 프레임 ID와 Figma 버전, 해시 | N04 |
| 1 → 2 | `design.md`, `tasks.md` 해시, 스프린트 백로그 | N15 |
| 2 → 3 | 완료 작업, 관문 증거, 기준과 달라진 점 목록 | N29 |
| 3 → 4 | 분류된 피드백 (어느 S·F를 겨냥하는지) | N33 |
| 4 → 다음 | 승격된 개선 항목, 새 하네스 버전 | N44 |

### 에이전트가 노드 하나를 처리하는 순서

1. `state.json`으로 현재 위치를 확인합니다.
2. `nodes.yaml`에서 그 노드의 정의를 찾습니다.
3. `4dd context <노드>`로 노드 지시문과 연결된 산출물만 읽습니다.
4. 작업하고 관문을 실행합니다.
5. 인계 기록과 증거를 원장에 남기고 다음 노드로 갑니다.

### 재사용 전 검증

노드가 산출물을 쓰기 전에, 현재 해시가 승인 당시 해시와 같은지 확인합니다. 다르면 "기준이 승인 없이 바뀐 것"이므로 진행을 멈추고 승인 노드로 돌아갑니다.

## 설계 ③ 가벼운 온톨로지 (G3, G14)

무거운 온톨로지(OWL/RDF, 그래프 DB)가 아니라 **정해진 타입의 ID, 그 사이의 관계, 통제된 어휘** 정도로 시작합니다.

회고의 진화 루프가 던지는 질문은 결국 "어떤 종류의 X가 어떤 노드에서 무슨 이유로 몇 번 실패했나" 같은 집계 질문입니다. 타입과 관계가 있으면 질의 한 번으로 답할 수 있습니다. 없으면 회고 때마다 에이전트가 로그 전체를 읽고 추측해야 해서 비싸고, 답도 매번 달라집니다.

### 엔티티 타입

괄호 안은 스키마에 쓸 이름입니다.

- 스토리 (`Story`)
- 요구사항 (`Requirement`, ID `R`)
- 시나리오 (`Scenario`, ID `S`)
- 프레임 (`Frame`, ID `F`)
- 컴포넌트 (`Component`, ID `C`)
- 작업 (`Task`, ID `T`)
- 테스트 (`Test`)
- 커밋 (`Commit`)
- 관문 실행 기록 (`GateRun`)
- 결정 (`Decision`)
- 피드백 (`Feedback`)
- 학습 항목 (`Learning`)

### 관계

- 요구사항은 스토리에서 나온다 (`derived_from`)
- 시나리오는 요구사항을 검증한다 (`verifies`)
- 프레임은 시나리오의 한 상태를 그린다 (`depicts`)
- 컴포넌트는 프레임에 쓰인다 (`used_in`)
- 컴포넌트는 코드 컴포넌트에 연결된다 (`maps_to`, Code Connect)
- 작업은 요구사항을 구현한다 (`implements`)
- 테스트는 시나리오를 확인한다 (`checks`)
- 관문 실행 기록은 (노드, 작업)을 평가하고, 결과와 원인을 남긴다 (`evaluates`)
- 결정은 요구사항이나 프레임을 바꾼다 (`changes`, 승인 필수)
- 학습 항목은 관문 실행 기록과 피드백에서 나오고 (`derived_from`), 승인되면 규칙으로 승격된다 (`promoted_to`)

### 추적 ID 붙이는 법

- `spec.md`의 요구사항에 `R1`, `R2` 같은 ID를 붙입니다.
- 시나리오에 `@R2` 태그를 답니다.
- `tasks.md`의 작업에 `T3 (R2)`처럼 요구사항 ID를 적습니다.
- 테스트도 같은 태그로 묶습니다.

그래프는 손으로 관리하지 않습니다. 파일에 붙인 ID(`@R2` 태그, 프레임 주석, 커밋 트레일러)와 원장에서 스캐너가 자동으로 뽑습니다. ID가 빠지면 관문의 추적 검사가 잡아냅니다.

### 실패 원인 통제 어휘

자유 텍스트로 쓰면 집계할 수 없으므로 정해진 단어만 씁니다. 어휘를 추가하려면 승인을 거칩니다.

| 어휘 | 뜻 | 기본 되돌림 |
|---|---|---|
| `code_bug` | 코드가 틀림 | N23 |
| `ui_mismatch` | 화면이 프레임과 다름 | N24 |
| `spec_ambiguous` | 스펙이 모호함 | N02 (사람 승인) |
| `spec_missing_state` | 스펙에 빠진 상태가 있음 | N02 (사람 승인) |
| `design_missing_state` | 그리지 않은 화면 상태가 있음 | N03F (사람 승인) |
| `test_flaky` | 테스트가 불안정함 | N22 |
| `env` | 실행 환경 문제 | 사람 호출 |
| `budget_exceeded` | 횟수 제한 초과 | 사람 호출 |

### 회고 진화 루프

1. **측정:** N42와 N43이 그래프에 질의합니다. 예를 들면 이런 질문들입니다.
   - `spec_ambiguous` 되돌림이 어떤 요구사항에 몰려 있나?
   - N26F 실패 중 `design_missing_state`가 차지하는 비율은?
   - Claude와 Codex는 각각 어느 노드에서 횟수 초과가 잦나?
   - 노드별 토큰 사용량과 걸린 시간은?
2. **후보:** 측정 결과를 근거로 학습 항목 후보를 `.4dd/learnings.md`에 만들고, 근거가 된 관문 실행 기록 ID를 함께 남깁니다.
3. **승격:** 사람이 승인하면 `nodes.yaml`, 노드 지시문, 관문, 스킬에 반영하고 하네스 버전을 올립니다.
4. **효과 검증:** 원장에 하네스 버전이 기록되어 있으므로, 다음 스프린트에 그 지표가 실제로 나아졌는지 버전 전후로 비교합니다. 나빠졌으면 되돌립니다.

에이전트가 혼자서 규칙을 늘리지 못하게 하는 장치이기도 합니다.

## 설계 ④ 에이전트가 하는 디자인 (G8~G11)

### Figma MCP에서 확인한 사실

2026-11-13 검색 기준입니다. 이 환경에는 Figma MCP가 연결돼 있지 않아 직접 확인하지는 못했습니다.

- **캔버스 쓰기:** 공식 원격 MCP 서버로 에이전트가 프레임, 컴포넌트, 변수, 오토 레이아웃을 만들고 고칠 수 있습니다. 베타 기능이고, 내 드래프트 밖에 쓰려면 Full 시트가 필요합니다. 베타 동안은 무료이지만 나중에 사용량 기반 유료로 바뀐다고 합니다.
- **읽기:** `get_design_context`는 기본으로 React + Tailwind 형태를 돌려주고, 스크린샷과 변수 정의도 읽을 수 있습니다. Code Connect로 Figma 컴포넌트를 실제 코드 컴포넌트에 연결합니다.
- **반대 방향:** 코드 화면을 Figma 레이어로 옮기는 도구(`generate_figma_design`)도 있습니다. 다만 클라이언트에 따라 보이지 않는다는 보고가 있습니다.
- **주의:** 도구 이름과 개수가 자료마다 달라서, 설치할 때 공식 문서로 다시 확인해야 합니다.

### 바뀌는 노드 (제안)

| 노드 | 내용 |

| N00F 디자인 시스템 준비 (신규, 프로젝트당 1회) | Figma 변수(색, 간격, 타이포)와 컴포넌트를 만들고, Code Connect로 코드 컴포넌트에 연결합니다. 이게 없으면 Figma → 코드 결과가 날것의 div 덩어리가 됩니다. |

| N24 UI 구현 | 고정된 버전의 프레임에서 `get_design_context`로 정보를 받아, Code Connect 컴포넌트로 구현합니다. |

### 순환 문제 (G10)

같은 에이전트가 그리고 구현하고 비교까지 하면 Figma 관문이 독립적인 검사가 되지 못합니다.

- **역할 분리:** 예를 들어 디자인은 Claude, 구현은 Codex가 맡습니다. 반대로 해도 됩니다.
- **버전 고정:** 구현 노드(N2x)에서는 고정된 버전의 Figma 프레임에 쓸 수 없게 잠급니다. 디자인을 바꾸려면 N03F로 되돌아가 결정 기록을 남기고 승인을 받아야 합니다.

## 설계 ⑤ 판단·통제·사람 접점 (G4~G7, G12, G13, G15)

### 관문 계약 (G4)

판단 노드마다 실행할 명령, 통과 조건, 남길 증거를 정합니다.

| 노드 | 관문 | 판정 방식 |
|---|---|---|
| N26 인수 테스트 | 해당 시나리오 태그로 E2E 실행 | 기계 (종료 코드) |
| N26F Figma 일치 | 첫 판정 + 기준선 (설계 ④) | 첫 판정은 비전 모델과 리뷰 에이전트, 이후 기계 |
| N27 스펙 일치 | 추적 검사 + 교차 리뷰 | 기계 + 다른 에이전트 |
| N28 DoD | 전체 테스트, 잠금 검사, 추적 검사 | 기계 |

### 되돌림과 횟수 제한 (G5)

- 실패 원인 어휘로 갈 곳을 정합니다 (설계 ③ 표 참고).
- N26F 실패는 N23이 아니라 N24로 보냅니다. 실패한 시각 테스트가 이미 Red 역할을 하므로, 화면을 조금 고치려고 단위 테스트부터 쓸 필요가 없습니다.
- 같은 관문에서 3번 실패하면 멈추고 사람을 부릅니다. 이때 실패 기록 요약을 함께 넘깁니다.
- "코드 문제"는 에이전트가 직접 되돌리고, "기준(스펙·디자인) 문제"는 에이전트가 판단만 한 뒤 사람이 승인해야 되돌립니다.

### 쓰기 잠금 (G6)

- 노드마다 수정할 수 있는 경로(`writes`)를 정합니다. 예를 들어 N23~N25에서는 `.feature`, `tests/acceptance/`, `spec.md`, 고정된 버전의 Figma 프레임을 고칠 수 없습니다.
- N28 관문에서 추가로 검사합니다: 테스트 수가 줄지 않았나, `.skip`이나 `only`가 새로 생기지 않았나, 기준선 이미지가 무단으로 바뀌지 않았나.

### 승인 3층 (G7, G12)

| 단계 | 누가 | 언제 |
|---|---|---|
| L0 기계 관문 | 하네스 | 매 반복마다 |
| L1 교차 리뷰 | 다른 에이전트 (Claude ↔ Codex) | 작업과 디자인이 끝날 때 |
| L2 사람 | PO, 디자이너, 개발 리드 | N04, N12, 스펙·디자인 변경, 횟수 초과, N33, 머지, 학습 항목 승격 |

사람만 할 수 있는 노드는 N01, N04, N33, N44입니다. 회고의 N42와 N43은 에이전트가 지표를 뽑아 초안을 만들고, 개선 항목을 정하는 건 사람이 합니다.

### 비개발자 입력 경로 (G12)

- **PO:** Git을 쓰지 않아도 됩니다. 채팅, Notion, 이슈 어디든 평범한 말로 스토리를 적으면, 에이전트가 `spec.md`와 `.feature` 초안으로 바꾸고 렌더링된 검토 페이지를 만듭니다. PO는 그 페이지에서 승인하거나 의견을 남깁니다.
- **디자이너 (일부 참여 시):** Figma에서 에이전트가 만든 프레임을 보고 고치거나 승인합니다.

### 프로필 (G13)

| 프로필 | 쓰는 노드 | 언제 |
|---|---|---|
| `full` | 전부 | 새 기능, 사용자에게 보이는 변경 |
| `lite` | Figma 노드 생략 → 디자인 시스템 기본값 사용, 회고 축소 | 작은 팀, 내부 도구, Figma 비용을 아낄 때 |
| `spike` | N21~N25만, 결과물은 버림 | 기술 검증 |

### 실행 도구 어댑터 (G15)

하네스가 특정 도구에 묶이지 않도록, 프로젝트마다 `4dd.config.yaml`에 명령을 등록합니다. 웹은 Playwright와 playwright-bdd로 시작하고, 모바일 앱은 다음 어댑터로 미룹니다.

```yaml
commands:
  unit: npm run test:unit
  acceptance: npx bddgen && npx playwright test
  visual: npx playwright test tests/visual
visual_tolerance: 0.01
profile: full
```

## 첫 MVP — 두 갈래를 나란히

1. **트랙 A: 상태와 온톨로지** (로그인 예시, Stage 2 루프)
   - 할 일: `nodes.yaml`(N21~N29), 원장, 인계 기록, 추적 ID, 실패 원인 어휘, `4dd context` 명령을 만듭니다.
   - 성공 기준: Claude가 하던 작업을 중간에 Codex가 원장만 보고 이어받아 N29까지 갑니다. 회고 질의 하나("실패 원인별 횟수")에 답할 수 있어야 합니다.
2. **트랙 B: Figma 기술 검증** (가장 큰 불확실성)
   - 할 일: 에이전트가 MCP로 변수와 컴포넌트 몇 개, 프레임 2개(`Login/Default`, `Login/Locked`)를 그립니다. 그다음 `get_design_context`와 Code Connect로 쓸 만한 코드가 나오는지 확인합니다.
   - 성공 기준: 생성된 코드가 디자인 시스템 컴포넌트를 쓰는지, 쓰기 베타가 안정적인지, 시트·요금 조건이 어떤지 확인합니다.

트랙 B 결과에 따라 N00F와 N03F의 세부 절차가 정해집니다.

## 자기 검토

### 1차 검토에서 찾은 문제와 바꾼 점

- 온톨로지를 RDF와 그래프 DB로 잡았는데, 운영 비용이 크고 에이전트가 직접 쓰기 어렵습니다. 파일 안 ID에서 자동으로 뽑는 인덱스로 줄였습니다.
- 인계 기록에 산출물 내용을 담으려 했는데, 토큰이 낭비되고 사본이 어긋납니다. ID와 해시로 가리키는 방식으로 바꿨습니다.
- 같은 에이전트가 디자인, 구현, 비교를 모두 하면 독립성이 사라집니다. 역할 분리와 버전 고정을 추가했습니다.
- 디자인 시스템 없이 바로 화면부터 그리면 Figma → 코드 품질이 낮습니다. N00F를 추가했습니다.

### 2차 검토에서 찾은 문제와 바꾼 점

- 진화 루프가 개선 효과를 측정할 수 없었습니다. 원장에 하네스 버전을 기록해 전후를 비교하게 했습니다.
- 실패 원인을 자유 텍스트로 쓰면 집계할 수 없습니다. 통제 어휘로 바꿨습니다.
- Figma 쓰기는 베타 이후 유료입니다. 프로필에서 끌 수 있게 했습니다.
- 목표가 진화하므로 스키마도 바뀔 것입니다. 원장과 그래프에 `schema_version`을 넣었습니다.

### 남은 위험

- Figma 쓰기 베타의 안정성과 요금, 도구 이름의 변동
- LLM이 그린 디자인이 무난하고 평범해지는 경향: 디자인 시스템과 참고 화면으로만 일부 보완할 수 있습니다.
- N27의 의미적 일치는 끝까지 완전 자동화가 어렵습니다.
- 쓰기 잠금도 설정 파일로 테스트를 제외하는 식으로 우회할 수 있습니다. 테스트 수 검사로 일부만 막습니다.
- 엔티티 타입이 시간이 지나며 불어나는 과잉 모델링: 타입 추가에도 승인을 받게 해야 합니다.
- 스프린트(1~4주)는 사람의 리듬입니다. 에이전트는 그 안에서 작업 루프를 여러 번 도는 것으로 보았는데, 이 해석은 확인이 필요합니다.

## 열린 결정

- **디자인 방향:** 지금 설계는 지시대로 "Figma 먼저 → 코드" 방향입니다. 트랙 B에서 쓰기 베타가 불안정하다고 나오면, 코드로 시안을 먼저 만들고 `generate_figma_design`으로 Figma에 옮겨 검토하는 역방향을 대안으로 검토할 수 있습니다. 지시와 다른 방향이므로 그때 근거를 보고 오너가 결정합니다.
- **되돌림 경로 변경:** N26F 실패를 N24로 보내는 것은 현재 절차를 바꾸는 제안입니다. 승인되면 [nodes.md](nodes.md)와 [workflow.md](workflow.md)에 반영합니다.
