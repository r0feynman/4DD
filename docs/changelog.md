## 2026-11-25 · 사람 개입을 줄이며 서비스를 완성하고 스스로 개선하기
- **새 노드:** N00
- **바뀐 노드:** N2D, N12, N32, N44
- 오너가 하네스 목표를 더 구체적으로 정했습니다: 사람 개입은 최소로 서비스를 완성하고, 스프린트마다 스스로 개선해 다음 스프린트와 비슷한 프로젝트에서는 루프를 덜 돕니다. 지금 노드를 이 목표에 대어 평가하고, 추천안대로 반영했습니다.
- N00 제품 목표와 완성 조건(프로젝트당 1회)을 새로 두었습니다. N32에서 진행도를 재고, 모두 채우면 N44에서 PO 승인 뒤 프로젝트를 마칩니다. 노드 맵에 `■ 서비스 완성` 표지를 그렸습니다.
- N2D 데일리 스크럼을 하네스가 원장으로 만드는 진행 요약으로 바꿨습니다. N12 준비 확인은 추적 검사가, 머지는 CI와 별도 리뷰 세션이 맡고 사람은 표본만 봅니다. 기준 변경은 늘 사람이 승인합니다.
- 하네스 설계에 설계 ⑥ 스스로 개선하는 루프(기록 → 후보 → 다시 돌려 보기 → 승격 → 정리 → 다른 프로젝트로 옮기기), 개선 지표 다섯 가지, 승격 등급, 시험 세트, 공통 층과 프로젝트 전용 층을 넣고, 설계 ⑦에 서비스 완성과 사람 승인 줄이기를 넣었습니다. 근거가 된 조사 출처를 함께 적었습니다.
- 첫 구현 범위(MVP)를 정했습니다: 원장에 관문 결과, 실패 원인, 사람 개입을 남기고 회고 때 개선 지표를 한 페이지로 보여 줍니다.

## 2026-11-24 · 되돌림 뒤 돌아오는 길과 남은 빈 곳
- **바뀐 노드:** N04, N22, N26F, N27, N33
- N27에서 설계 스펙(`design.md`) 자체가 틀렸을 때 쓰는 실패 원인 `arch_wrong`(→ N13, 사람 승인)을 더해 10개가 됐습니다. 기본은 설계대로 코드를 고칩니다(`code_bug`, N23). 노드 맵의 경로 이름을 "스펙 변경"에서 "설계가 틀림 · 사람 승인"으로 바꿨습니다. N12 → N01은 단어 없이 팀이 판단합니다.
- 개발 중에 Stage 0으로 돌아간 작업은 N04에서 다시 승인받으면 스프린트 플래닝을 다시 하지 않고 원래 작업의 N22로 돌아옵니다. 노드 맵에 `↪ N22` 표지로 그렸고, 실패 원인 표에 "고친 뒤" 칸을 더했습니다.
- 화면을 고치다 동작까지 바뀌면 N03W·N03F 대신 N03(시나리오)부터 고칩니다. N04와 N26F에 이 경로를 더했습니다.
- N33 이해관계자 피드백은 되돌리지 않고 항상 회고(N41)로 갑니다. 새 요구와 화면 수정은 다음 스프린트의 Stage 0에서 다룹니다. 그래서 되돌림 경로가 8개에서 7개가 됐습니다.
- `test_flaky`로 N22에서 테스트를 고친 뒤에는 TDD 루프를 거치지 않고 N26으로 바로 갑니다.
- 모두 2026-11-23 점검에서 찾은 빈 곳이고, 오너가 추천안대로 정했습니다.

## 2026-11-23 · N26F가 프레임과 다를 때, 화면이 없는 작업 유형
- **바뀐 노드:** N26F
- N26F에서 화면이 프레임과 다르면 기본은 프레임대로 다시 구현합니다(화면 차이 N24, 로직 오류 N23). N03F로 가는 길은 프레임 자체가 틀렸을 때만 쓰고, 사람이 승인해야 갑니다. 이 길의 이름을 "디자인 변경"에서 "프레임이 틀림 · 사람 승인"으로 바꿨습니다(오너 결정).
- 실패 원인에 `design_wrong`(프레임 자체가 틀림 → N03F, 사람 승인)을 더해 9개가 됐습니다(오너 승인). `ui_mismatch`(구현을 고침)와 헷갈리지 않게 가르는 기준도 적었습니다.
- 화면이 없는 작업 유형(백엔드 등)은 Figma 노드 5개를 건너뛰고 N03 → N04, N26 → N27, N31 → N32로 갑니다. 하네스 설계에만 있던 규칙을 `workflow.md`로 옮기고, 노드 맵과 워크플로 페이지에도 그렸습니다. 용어집에 "작업 유형"을 더했습니다.
- CLI, 라이브러리처럼 정하지 않은 작업은 유형을 더하지 않고, 화면이 없으면 백엔드와 같이 다룹니다(오너가 추천안으로 결정).
- 검사를 더했습니다: 건너뛰는 노드가 Figma 노드와 빠짐없이 같은지, 대신 가는 경로가 건너뛴 노드의 바로 앞뒤를 잇는지.
- 사이트의 N12 되돌림 조건에 빠졌던 "화면"을 넣었습니다.

## 2026-11-23 · 노드 맵을 시안 나로
- 오너가 노드 맵 시안 중 나(위에 고리, 아래에 세부)를 골랐습니다. 임시로 두었던 시안 B를 바꿉니다. 시안과 조사는 아티팩트 [노드 맵 시안 가·나](https://claude.ai/artifact/MqYVwCtiEX39J4V7iJrjge)와 [노드 맵 구조 조사](https://claude.ai/artifact/KeYSAAwVgsPSooZuf95UcU)에 있습니다.
- 위에 스프린트 고리(Stage 0 → 4 → 다음 스프린트)가 있고, 스테이지를 누르면 아래에 그 스테이지의 노드가 순서대로 열립니다.
- 굵은 선은 앞으로 가는 경로만 긋습니다. 돌아가는 경로는 노드 옆 표에 ↩ 표지로 적고, 노드를 누르면 그 노드의 돌아가는 경로만 왼쪽에 곡선으로 나타납니다. 곡선은 노드에 붙이지 않고 띄워서 둥글게 그립니다(오너 요청).
- 루프 상자는 용어집의 TDD 루프(N23 → N24 → N25)만 묶습니다. 오너가 2026-11-18에 정했습니다.
- 그리는 코드는 `docs-view/nodemap.js`로 바꿨고 `docs-view/metro.js`는 지웠습니다. 빌드 검사에 두 가지를 더했습니다: 굵은 선이 원본의 앞으로 가는 경로와 같은지, TDD 루프가 한 스테이지 안에 순서대로 이어져 있는지.

## 2026-11-18 · Stage 0은 매 스프린트의 첫 스테이지
- **바뀐 노드:** N44
- 오너가 정했습니다: Stage 0 백로그 정리는 수시로 하는 활동이 아니라 매 스프린트의 첫 스테이지이고, 스프린트 플래닝 전에 합니다. 스프린트는 그대로 Stage 0~4로 이루어집니다.
- 회고가 끝나면 N44에서 다음 스프린트의 N01로 갑니다. 전에는 N11로 갔습니다.
- 아래 항목에서 아티팩트 노드 맵에 넣었던 "수시 노선", "스프린트와 병행"은 원본에 없던 해석이라 뺐습니다. "본선", "지선"도 용어집에 없는 말이라 용어집의 말(경로, 반복 노드, 프로젝트당 1회)로 바꿨습니다.

## 2026-11-18 · 아티팩트 노드 맵에 시안 B를 임시로

- 스테이지 구역이나 버튼을 누르면 그 스테이지가 넓어지고 이름과 갈 곳이 자세히 보입니다.

- 그림 데이터는 그대로 `docs/workflow.md` 노드 맵에서 만들어지고, 그리는 코드는 `docs-view/metro.js`에 있습니다.

## 2026-11-18 · 노드 맵 스테이지 순서 바로잡기
- 노드 맵이 Stage 4 → 1 → 2 → 3 → 0 순으로 뒤섞여 그려지던 문제를 고쳤습니다. 이제 왼쪽부터 Stage 0 → 4 순서이고, 각 스테이지 안에서는 위에서 아래로 진행합니다.
- 원인은 앞 스테이지로 거꾸로 가는 긴 화살표였습니다. 이런 되돌림은 화살표 대신 점선 상자 `↩ N02` 같은 표지로 그립니다.
- 검사를 추가했습니다: 노드 맵에 앞 스테이지로 거꾸로 가는 화살표가 생기거나, `workflow.md`와 사이트의 노드 맵이 서로 다르면 빌드와 검사가 실패합니다.
