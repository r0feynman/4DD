# 하네스 첫 구현 조각 명세

> **상태 (2026-11-25):** 오너가 실행 방식, 구현 언어, 시험 대상, 코드 위치를 정했고, 이 명세를 바탕으로 구현을 시작했습니다. 구현 1단계(시험 프로젝트와 추적 ID 검사)와 2단계(노드 정의, 원장, `state.json`)를 마쳤고, 진행은 [harness/README.md](../harness/README.md)에 적습니다. 설계의 근거는 [harness-design.md](harness-design.md)에 있고, 이 문서는 그 설계를 코드로 옮기는 방법만 적습니다.

**구현 조각**은 하네스 전체를 한 번에 만들지 않고, 처음부터 끝까지 실제로 도는 작은 범위로 잘라 만든 것입니다. 첫 조각은 **백엔드 기능 하나가 Stage 2(N21~N29)를 사람 손 없이 도는 것**입니다. Figma와 에뮬레이터는 가장 불확실한 부분이라 빼고, 핵심 루프(상태, 관문, 횟수 제한, 원장)부터 싸게 검증합니다. 하네스 설계에서 정한 첫 구현 범위(MVP, 원장 기록과 지표 보고)도 이 조각에 들어갑니다. 그 기록을 만들어 낼 최소한의 루프를 함께 만드는 셈입니다.

## 정한 것

| 항목 | 결정 | 이유 |
|---|---|---|
| 실행 방식 | 지휘 프로그램 + 작업당 세션 | 지휘 프로그램(`4dd run`)이 상태를 들고 노드를 진행합니다. 작업 노드는 작업 하나당 세션 하나로 이어서 하고, 관문은 지휘 프로그램이 직접 돌리고, 설계 대조(N27)는 별도 리뷰 세션이 맡습니다. 통제와 토큰 비용의 균형 |
| 구현 언어 | Node (TypeScript) | Expo 프로젝트와 같은 실행 환경. npm 패키지로 배포하면 공통 층을 옮기기 쉬움 |
| 시험 대상 | 예시 로그인 백엔드 | 정답을 알고 있어 하네스 자체를 검증하기 좋음 |
| 코드 위치 | 이 저장소의 `harness/` | 설계 문서와 함께 고치고, 안정되면 npm 패키지로 뗌 |

## 범위

- **하는 것:** 작업 유형 `backend`, Stage 2의 N21~N29(N26F는 건너뜀), 쓰기 잠금, 횟수 제한, 실패 원인 분류, 사람 호출과 재개, 원장, 지표 보고, Claude와 Codex 두 도구
- **하지 않는 것:** Stage 0·1·3·4, N2D, Figma와 화면 비교, 모바일, 비개발자 승인 통로, 시험 세트, 학습 승격, 공통 층. 다음 조각에서 차례로 붙입니다(아래 「다음 조각」).

Stage 0·1의 산출물(`spec.md`, `.feature`, `design.md`, `tasks.md`)은 사람이 미리 만들어 둔 것을 승인된 것으로 봅니다. `4dd init`이 이 파일들의 해시를 스테이지 패킷(1 → 2)으로 고정합니다.

## 구조

```
사람 ─ 4dd run ─▶ 지휘 프로그램 ─┬─▶ 작업 세션 (Claude 또는 Codex, 작업당 1개)
                                 │       └─ 훅 ─▶ 4dd check (쓰기 잠금)
                                 ├─▶ 관문 (지휘 프로그램이 직접 실행)
                                 ├─▶ 리뷰 세션 (N27, 읽기 전용, 매번 새로)
                                 ├─▶ 원장 .4dd/events.jsonl ─▶ state.json
                                 └─▶ 사람 호출 (멈춤) ◀─ 4dd human
```

| 부분 | 하는 일 |
|---|---|
| 지휘 프로그램 | `state.json`과 `nodes.yaml`로 다음 노드를 정하고, 세션에 노드 지시를 보내고, 관문을 돌리고, 통과한 노드마다 커밋합니다. 에이전트는 다음 노드로 넘어가거나 판정하지 않습니다 |
| 작업 세션 | 작업 노드(N22~N25)를 처리합니다. 노드 하나가 세션의 한 차례입니다. 같은 작업 안에서는 세션을 이어 써서 맥락을 다시 읽지 않습니다 |
| 리뷰 세션 | N27에서 `design.md`와 작업의 변경분만 보고 설계와 맞는지 판정합니다(승인 L1). 읽기 전용이고 작업 세션과 맥락을 나누지 않습니다 |
| `4dd check` | 훅, git 훅, 지휘 프로그램이 모두 부르는 잠금 검사입니다. 규칙은 이 한 곳에만 있습니다 |
| 원장 | 모든 사실을 한 줄씩 추가만 합니다. `state.json`과 지표는 원장에서 다시 만듭니다 |

## 노드마다 누가 무엇을

| 노드 | 누가 | 고칠 수 있는 곳 | 통과 조건 | 실패하면 |
|---|---|---|---|---|
| N21 | 하네스 | `.4dd/` | `tasks.md`에서 체크되지 않은 첫 작업을 고름 | — |
| N22 | 작업 세션 | `tests/acceptance/**` | 작업의 시나리오(`@S`)마다 인수 테스트가 있고, 돌리면 **실패**함 | 같은 노드 다시 |
| N23 | 작업 세션 | `tests/unit/**` | 새 단위 테스트가 있고 돌리면 **실패**함 | 같은 노드 다시 |
| N24 | 작업 세션 | `src/**` | 단위 테스트 전부 통과 | 같은 노드 다시 |
| N25 | 작업 세션 | `src/**` | 단위 테스트 전부 통과, 테스트 수 그대로 | 같은 노드 다시 |
| N26 | 하네스 | — | 작업의 인수 테스트 통과. 실패하면 한 번 다시 돌려 결과가 바뀌면 `test_flaky` | `code_bug` → N23 · `test_flaky` → N22 · 그 밖의 원인은 분류 차례로 |
| N27 | 리뷰 세션 | 없음 (읽기 전용) | 변경분이 `design.md`와 맞음 | `code_bug` → N23 · `arch_wrong` → 사람 승인 |
| N28 | 하네스 | — | DoD: 인수·단위 테스트 전체 통과, TDD 순서(N23 실패 뒤 N24 통과)가 원장에 있음, 테스트 수가 작업 시작 때보다 줄지 않음, 건너뛰기 표시가 새로 없음, 잠긴 파일 해시 그대로 | `code_bug` → N23 |
| N29 | 하네스 | `specs/**/tasks.md` | 작업을 체크하고 남은 작업이 있으면 N21, 없으면 조각 끝 | — |

- 작업 노드의 "같은 노드 다시"는 관문 출력(실패한 테스트 이름과 메시지)을 붙여 같은 세션에 한 번 더 시키는 것입니다. 판단 노드의 횟수 제한과 같이 셉니다.
- 사람 승인이 필요한 원인(`spec_ambiguous`, `spec_missing_state`, `arch_wrong`, `env`, `budget_exceeded`)이 나오면 지휘 프로그램은 멈추고 사람을 기다립니다. 첫 조각에는 Stage 0·1이 없으므로 사람이 스펙이나 설계를 직접 고칩니다. `4dd human approve`로 다시 시작하면 스펙 쪽 원인은 원래 작업의 N22로, `arch_wrong`은 사람이 `design.md`와 `tasks.md`를 맞춘 뒤 N21로 돌아갑니다. 승인할 때 잠긴 파일의 기준 해시를 새로 고정합니다.
- 횟수 제한은 [workflow.md](workflow.md#횟수-제한) 그대로입니다: 판단 노드 연속 3회, 작업 전체 10회, `test_flaky` 자동 재실행 1회는 세지 않음.

### `nodes.yaml` 형식

설계 ①의 형식을 따릅니다. 위 표를 옮긴 [harness/nodes/nodes.yaml](../harness/nodes/nodes.yaml)이 원본이고, 노드 순서는 파일에 적힌 순서입니다. 두 노드만 예로 적습니다.

```yaml
version: 0.1.0
defaults: {budget: 3, task_budget: 10, flaky_retries: 1, turn_timeout_min: 15}

N24:
  name: Green · 통과하게 구현
  stage: 2
  method: tdd
  kind: work
  actor: worker                # harness | worker | reviewer
  instruction: instructions/N24.md
  reads: [task, requirements, scenarios, design, last_gate, hint]
  writes: ["src/**"]
  gate:
    run: "{commands.unit}"
    expect: pass               # pass면 명령이 성공해야, fail이면 실패해야 통과

N26:
  name: 인수 테스트 통과?
  stage: 2
  method: bdd
  kind: decision
  actor: harness
  gate:
    run: "{commands.acceptance} {task.scenario_files}"
    expect: pass
    flaky_rerun: true
  on_fail:
    - when: code_bug
      goto: N23
    - when: test_flaky
      goto: N22
      then: N26
    - when: [spec_ambiguous, spec_missing_state, env]
      goto: human
      then: N22
```

- **관문:** `run`은 명령 하나나 목록이고, `checks`로 추가 검사를 붙입니다(`scenario_files_exist`, `new_tests`, `test_count_kept`, `tdd_order`, `no_new_skips`, `locked_unchanged`).
- **작업 노드:** 관문을 못 채우면 같은 노드를 다시 하므로 `on_fail`을 두지 않습니다. 판단 노드는 `on_fail`이 꼭 있어야 합니다.
- **다음 노드:** 기본은 파일 순서에서 이 작업 유형에 켜지는 다음 노드이고, `next`로 바꿉니다(N29 → N21).
- **형식 검사:** 하네스가 읽을 때 검사하고, 문제를 모두 모아 알립니다. 통제 어휘에 없는 원인, 없는 노드로 가는 경로, 승인 뒤 갈 곳(`then`)이 없는 사람 경로, 지시문이 없거나 파일이 없는 세션 노드, 관문 없는 작업 세션 노드를 잡습니다.

### 노드 지시문

노드 지시문은 `harness/nodes/instructions/<노드>.md`에 둡니다. 모든 지시문은 같은 네 칸으로 씁니다. 승격된 학습은 「주의점」에 ID와 함께 한 줄씩 붙습니다.

```md
# N24 Green · 통과하게 구현

## 목표
N23에서 실패하게 만든 단위 테스트를 통과시키는 가장 작은 코드를 씁니다.

## 할 것
- 아래 「이번 작업」의 요구사항과 설계를 따릅니다.
- 실패한 테스트 출력이 있으면 그 원인부터 고칩니다.

## 하지 말 것
- `src/` 밖을 고치지 않습니다. 테스트, 스펙, 설정은 잠겨 있습니다.
- 커밋하지 않습니다. 하네스가 합니다.

## 주의점
- (L12) 잠금 시간은 서버 시계로 계산한다
```

`4dd context <노드> --task <작업>`이 지시문 뒤에 「이번 작업」을 붙여 세션에 보냅니다: 작업 줄, 관련 요구사항(`R`) 줄, 관련 시나리오(`@S`), `design.md`, 지난 관문 출력, 사람 힌트. 파일 전체가 아니라 ID로 찾은 조각만 넣고, 원장에는 넣은 것의 ID와 해시만 남깁니다(`loaded`).

## 시험 프로젝트와 추적 ID

`harness/fixtures/login-backend/`에 시험 프로젝트 원본을 두고, `4dd init`이 이것을 새 git 저장소로 복사해 돌립니다. 그래야 몇 번이든 같은 출발점에서 다시 돌릴 수 있고, 나중에 시험 세트로 그대로 씁니다.

```
4dd.config.yaml
specs/login/spec.md        # R1~R3
specs/login/login.feature  # @S1~@S3, 시나리오마다 @R 태그
specs/login/design.md
specs/login/tasks.md       # T1 (R1), T2 (R2), T3 (R3)
src/  tests/unit/  tests/acceptance/   # 처음엔 비어 있음
```

- 추적 ID는 설계 ③대로 붙입니다: 요구사항 `R1`, 시나리오 태그 `@S1 @R1`, 작업 `T1 (R1)`. 저장소의 예시 템플릿(`templates/specs/example/`)에도 같은 ID를 붙였습니다. 인수 테스트 파일 이름은 시나리오 ID를 씁니다(`tests/acceptance/S1.test.ts`).
- **작업의 시나리오:** 시나리오는 그 요구사항을 다루는 작업 가운데 `tasks.md`에서 가장 뒤에 있는 작업이 통과시킵니다. 요구사항 하나를 작업 여럿이 나눠 맡으면(예: API 작업과 화면 작업) 마지막 작업에서야 시나리오가 통과할 수 있기 때문입니다. 통과시킬 시나리오가 없는 앞 작업은 추적 검사가 주의로 알립니다.
- **추적 검사:** `4dd check trace`가 요구사항, 시나리오, 작업의 ID가 빠짐없이 이어졌는지 봅니다. 태그가 없거나 겹치는 ID, `spec.md`에 없는 요구사항, 시나리오나 작업이 없는 요구사항은 오류입니다.
- 백엔드는 Node + Fastify, 테스트는 Vitest와 Supertest로 합니다. 지휘 프로그램은 `commands`만 부르므로 다른 스택으로 바꿔도 하네스는 그대로입니다.

```yaml
# 4dd.config.yaml
work_type: backend
profile: full
agent: claude                 # claude | codex
commands:
  unit: npx vitest run tests/unit
  acceptance: npx vitest run tests/acceptance
locked: ["specs/**", "4dd.config.yaml", ".4dd/**", ".claude/**", ".codex/**", ".githooks/**"]
```

`locked`는 모든 노드에 걸리고, 노드의 `writes`에 적힌 경로만 그 노드에서 풀립니다. 예를 들어 `tasks.md`는 N29에서 하네스만 고칠 수 있습니다.

## `4dd` 명령

| 명령 | 누가 부르나 | 하는 일 | 종료 코드 |
|---|---|---|---|
| `4dd init <폴더>` | 사람 | 시험 프로젝트 복사, 훅 설치, 잠긴 파일 해시 고정, `.4dd/` 만들기 | 0 성공 · 1 오류 |
| `4dd run [--agent claude\|codex]` | 사람 | 지휘 루프. 끝나거나 사람이 필요할 때까지 돎 | 0 끝 · 3 사람 대기 · 1 오류 |
| `4dd status` | 사람 | 지금 작업과 노드, 기다리는 이유 | 0 |
| `4dd human <approve\|hint\|reclassify\|hold>` | 사람 | 사람 개입을 원장에 남기고 재개할 수 있게 함 | 0 · 1 잘못된 입력 |
| `4dd report` | 사람 | 원장으로 지표와 질의 결과를 `.4dd/report.md`에 씀 | 0 |
| `4dd context <노드> --task <작업>` | 지휘 프로그램 | 세션에 보낼 지시문과 「이번 작업」 출력, `loaded` 기록 | 0 |
| `4dd gate <노드> --task <작업>` | 지휘 프로그램 | 관문 실행, 관문 실행 기록 남김 | 0 통과 · 1 실패 |
| `4dd check <trace\|path\|bash\|session\|commit>` | 훅, git 훅, 지휘 프로그램 | 추적 ID 검사와 잠금 검사, 훅 실행 기록 남김 | 0 허용 · 2 막음 (이유는 stderr) |

종료 코드 2로 막는 방식은 Claude 훅과 Codex 훅이 둘 다 지원합니다. 그래서 같은 `4dd check`를 두 도구에 그대로 겁니다.

## 도구 어댑터

| | Claude | Codex |
|---|---|---|
| 첫 차례 | `claude -p --output-format json --session-id <uuid>` | `codex exec --json -C <폴더> -s workspace-write` |
| 이어 쓰기 | `claude -p --resume <uuid>` | `codex exec resume <id>` |
| 리뷰 세션 | `--allowedTools Read Grep Glob`, `--json-schema` | `-s read-only`, `--output-schema` |
| 훅 넣기 | `--settings harness/hooks/claude.json` (PreToolUse, SessionStart) | 프로젝트 `.codex/hooks.json` (PreToolUse, SessionStart) |
| 토큰과 시간 | 결과 JSON의 사용량과 걸린 시간 | `--json` 이벤트의 사용량 |
| 막는 명령 | `--disallowedTools "Bash(git commit:*)" "Bash(git push:*)"` | `4dd check bash` 훅으로 같은 명령을 막음 |

- **파일 경로 읽기:** Claude의 편집 도구는 `tool_input.file_path`, Codex의 `apply_patch`는 `tool_input.command` 안의 패치 머리(`*** Update File: …`)에서 경로를 읽습니다.
- **Codex 훅 신뢰:** Codex는 신뢰하지 않은 훅을 건너뜁니다. `4dd init`이 사람에게 `/hooks`에서 한 번 신뢰하라고 안내하고, 세션 시작 훅(`4dd check session`)이 원장에 한 줄을 남기게 합니다. 첫 차례 뒤 그 줄이 없으면 훅이 꺼진 것이므로 `env`로 멈춥니다. 신뢰 확인을 건너뛰는 옵션은 쓰지 않습니다.
- **차례 시간 제한:** 한 차례가 `turn_timeout_min`(15분)을 넘으면 끊고 `env`로 기록합니다.

## 잠금을 지키는 겹

```
훅 (고치기 직전) ─▶ 차례 뒤 변경 검사 ─▶ git pre-commit ─▶ N28 DoD ─▶ CI
```

- **훅:** 가장 빨리 막아 차례를 아낍니다. 다만 셸 명령으로 파일을 쓰면 놓칠 수 있습니다.
- **차례 뒤 변경 검사:** 노드가 고칠 수 없는 곳이 바뀌었으면 되돌리는 결정적인 겹입니다. 차례가 끝나면 지휘 프로그램이 `git status`로 바뀐 파일을 보고, 노드의 `writes` 밖이 바뀌었으면 되돌리고 훅 실행 기록(`check: diff_lock`, `blocked`)을 남긴 뒤 그 노드를 다시 시킵니다. 횟수 제한에 셉니다. 차례를 시작할 때 작업 트리가 깨끗해야 하므로, 지휘 프로그램이 통과한 노드마다 커밋합니다.
- **git pre-commit:** 커밋할 때 같은 잠금 검사를 다시 합니다. 사람이나 다른 경로로 들어온 변경도 막습니다.
- **N28 DoD:** 테스트를 지우거나 건너뛰게 만들어 통과하는 것을 막습니다.
- **CI:** 건너뛸 수 없는 마지막 겹입니다. git 훅을 건너뛴 변경도 여기서 걸립니다.

## 실패 원인 분류

판단 노드가 실패하면 원인을 정하는 차례가 한 번 더 있습니다.

1. 기계로 정할 수 있으면 기계가 정합니다. 인수 테스트를 다시 돌려 결과가 바뀌면 `test_flaky`, 테스트 실행기 자체가 안 뜨면 `env`입니다.
2. 아니면 작업 세션에 그 노드의 `on_fail`에 있는 단어만 고르게 합니다(정해진 출력 형식: 원인 하나와 근거 300자 이하). 고르지 못하면 기본 원인(N26과 N28은 `code_bug`)입니다.
3. 사람 승인이 필요한 원인이면 멈춥니다. 에이전트가 풀기 어려운 문제를 엉뚱한 원인으로 분류해 빠져나가지 못하게 하기 위해서입니다.

## 원장 이벤트

한 줄에 하나, 추가만 합니다. 모든 줄에 `ts`, `schema_version`, `harness`(하네스 버전)가 붙습니다. 내용은 남기지 않고 ID, 해시, 숫자만 남깁니다. 사람 힌트 글은 `.4dd/human/<ID>.md`에 두고 원장에는 해시만 적습니다.

| 이벤트 | 언제 | 주요 필드 |
|---|---|---|
| `run_start` | `4dd run` 시작 | `run`, `agent`, `feature` |
| `node_start` | 노드 진입 | `id`, `node`, `task`, `session` |
| `node_end` | 노드 종료 | `id`, `result`, `cause`, `task_done`(N29), `loaded`, `tokens`, `minutes`, `turns` |
| `gate_run` | 관문 실행 | `id`, `node`, `task`, `run`, `exit`, `result`, `flaky_rerun`, `tests` |
| `hook_run` | 잠금 검사 | `id`, `hook`, `check`(`trace`, `path`, `bash`, `session`, `commit`, `diff_lock`), `run`, `target`, `result` |
| `classify` | 실패 원인 정함 | `run`, `cause`, `by`, `needs_human` |
| `human` | 사람 개입 | `id`, `node`, `task`, `kind`(`approve`, `edit`, `hint`, `reject`, `reclassify`, `hold`), `reason`, `minutes` |
| `commit` | 노드 통과 뒤 커밋 | `sha`, `node`, `task` |
| `run_end` | 루프 멈춤 | `reason` (`done`, `wait_human`, `error`, `stopped`) |

- **ID:** 종류마다 앞글자와 번호를 붙입니다. 루프 `RUN`, 노드 실행 `NR`, 관문 실행 `GR`, 훅 실행 `HR`, 사람 개입 `HU`. 번호는 원장에서 가장 큰 번호 다음입니다.
- **형식 검사:** 하네스는 형식이 틀린 이벤트를 원장에 쓰지 않습니다. 읽을 때 중간 줄이 깨졌거나 더 새 하네스가 쓴 줄이 있으면 멈추고, 마지막 줄만 깨졌으면(쓰다 끊김) 주의를 남기고 넘어갑니다.
- **`state.json`:** 지금 작업과 노드, 세션 ID, 노드별 연속 실패 수, 작업 전체 되돌림 수, 기다리는 이유, 마지막으로 실패한 관문, 끝낸 작업과 보류한 작업을 담습니다. 원장을 차례로 접어 만들기 때문에 언제든 다시 만들 수 있어서, 세션이나 지휘 프로그램이 죽어도 `4dd run`이 그 자리부터 이어 갑니다. 접은 이벤트 수를 함께 적어 두고, 원장이 그보다 길면(저장 전에 죽음) 원장에서 다시 만듭니다.
- **횟수 세기:** 노드가 실패할 때마다 그 노드의 연속 실패 수와 작업 전체 되돌림 수를 하나씩 올립니다. 통과하면 그 노드만 0으로, 작업이 끝나면 모두 0으로 돌아갑니다. 사람이 승인하거나 힌트를 주면 그 노드와 작업의 횟수를 새로 줍니다. 그러지 않으면 다시 시도하자마자 한도에 걸리기 때문입니다.
- **커밋 트레일러:** `4DD-Node: N24`, `4DD-Task: T2`, `4DD-Refs: R2,S2`, `4DD-Run: NR88`
- **재사용 전 검증:** 노드를 시작할 때마다 잠긴 파일 해시를 기준 해시와 비교합니다. 다르면 기준이 승인 없이 바뀐 것이므로 멈추고 사람을 부릅니다. 기준 해시는 `init` 때 고정하고, 사람이 승인할 때와 N29가 `tasks.md`에 체크만 했을 때 새로 적습니다.

## 사람이 하는 일

첫 조각의 사람은 터미널을 쓰는 개발자 한 명입니다. 비개발자 승인 통로는 Stage 0이 붙는 조각 2에서 만듭니다.

| 언제 | 사람이 하는 일 | 명령 |
|---|---|---|
| 시작 | 프로젝트를 만들고 Codex면 훅을 한 번 신뢰 | `4dd init`, Codex `/hooks` |
| 횟수 초과 | 힌트를 주고 다시 시도, 원인 바로잡기, 보류 | `4dd human hint "<글>"` · `reclassify <원인>` · `hold` |
| 사람 승인 원인 | 스펙이나 설계를 고친 뒤 승인 | `4dd human approve` |
| 끝 | 지표 보기 | `4dd report` |

사람이 준 힌트는 설계 ⑥대로 바로 학습 후보가 됩니다. `4dd human hint`가 `.4dd/learnings.yaml`에 `status: candidate` 항목을 근거 ID(노드 실행, 관문 실행 기록)와 함께 더합니다. 후보를 지시문 「주의점」으로 올리는 것은 이 저장소에 PR을 올려 오너가 승인하고, 하네스 버전을 올립니다.

## 자기 검토

### 1차 검토에서 찾은 문제와 바꾼 점

- **훅만으로는 잠금을 지킬 수 없음:** 셸 명령으로 파일을 쓰면 편집 훅을 피합니다. 지휘 프로그램이 차례마다 바뀐 파일을 검사하고 되돌리는 겹을 더해 이것을 결정적인 겹으로 삼았습니다.
- **에이전트의 커밋:** 에이전트가 커밋하면 `--no-verify`로 git 훅을 건너뛸 수 있습니다. 에이전트의 커밋을 막고 지휘 프로그램이 통과한 노드마다 커밋하게 했습니다. 그러면 원장과 커밋도 트레일러로 이어집니다.
- **노드마다 새 세션:** 맥락을 매번 다시 읽어 비쌉니다. 작업 하나 안에서는 세션을 이어 쓰고, 판정이 독립적이어야 하는 N27만 새 세션으로 했습니다.
- **두 도구를 동시에 맞추기:** 실패 원인이 하네스인지 도구인지 가르기 어렵습니다. Claude로 루프를 먼저 끝내고 Codex를 붙이게 했습니다.

### 2차 검토에서 찾은 문제와 바꾼 점

- **Codex 훅 신뢰:** 신뢰 확인을 건너뛰는 옵션은 위험합니다. 사람이 한 번 신뢰하고, 세션 시작 훅이 원장에 남긴 줄로 훅이 켜져 있는지 확인하게 했습니다.
- **분류를 작업 세션이 함:** 빠져나갈 유인이 있습니다. 고를 수 있는 단어를 그 노드의 `on_fail`로 좁히고, 앞 스테이지로 가는 원인은 사람이 승인하게 해서 막았습니다.
- **끝나지 않는 차례:** 차례마다 시간 제한을 두고 넘으면 `env`로 멈추게 했습니다.
- **비개발자 입력 경로가 없음:** 첫 조각에는 Stage 0이 없어 필요하지 않습니다. 조각 2의 범위로 명시했습니다.

### 남은 위험

- 실제 토큰 비용은 돌려 봐야 압니다. 첫 조각의 원장이 그 기준선입니다.
- 백엔드에서 맞춘 루프가 모바일의 느린 빌드와 화면 비교에서도 그대로 통할지는 조각 3에서 확인합니다.
- Codex의 비대화형 실행에서 훅이 어떻게 동작하는지는 공식 문서에 없어 직접 확인해야 합니다.
