# 하네스 조각 3 명세

> **상태 (2026-11-27):** 오너가 시험 대상, Figma 위치, 웹을 시험하는 방식, 디자인 시스템을 확인하는 방식을 정했고(2026-11-26), 이 명세가 제안한 일곱 가지도 그대로 승인했습니다(2026-11-27). 1~8단계를 마쳤습니다. Claude 실제 실행(각본 PO)으로 화면 기능 「로그인 화면」 하나를 스토리부터 디자인, Android·웹 구현, 화면 비교까지 끝냈고, 거기서 찾은 하네스 문제를 고쳤습니다(아래 「구현하며 확인할 것」). 남은 것은 9단계(고친 하네스로 다시, Codex, 오너가 PO인 실행)입니다. 앞 조각은 [harness-slice1.md](harness-slice1.md)와 [harness-slice2.md](harness-slice2.md)에, 설계의 근거는 [harness-design.md](harness-design.md)의 설계 ④(에이전트가 하는 디자인)에 있습니다.

조각 3은 **화면이 있는 기능을 Figma 디자인부터 앱 구현과 화면 비교까지 사람 손 없이 가는 것**입니다. 에이전트가 디자인 시스템을 만들고(N00F), 시나리오마다 와이어프레임과 완성 화면을 Figma에 그립니다(N03W, N03F). PO는 N04 검토 페이지에서 스펙, 시나리오, 화면 이미지를 함께 보고 승인합니다. 승인하면 화면 이미지가 고정되고, 구현 세션은 그 이미지대로 React Native 화면을 만듭니다. 가상 기기에서 Maestro가, 웹에서 Playwright가 시나리오를 눌러 보고(N26), 찍은 화면을 고정된 이미지와 비교합니다(N26F). 사람 손은 조각 2와 같이 스토리 한 번과 승인 두 번입니다.

## 범위

- **하는 것:** 작업 유형 `mobile`(Android)과 `web`(Expo 웹), 기능마다 작업 유형, N00F·N03W·N03F·N26F, 승인 때 고정하는 프레임 이미지, Expo 로컬 빌드(가상 기기에 설치), Maestro 인수 테스트, Playwright 인수 테스트, 화면 비교, N04 검토 페이지의 화면 이미지와 디자인 시스템, 작업 세션은 Claude와 Codex 두 도구
- **하지 않는 것:** iOS, Stage 3·4(N31F 포함), 프로필 `lite`·`spike`, 디자이너가 Figma에서 직접 고치는 흐름, 디자인 시스템을 나중에 넓히는 절차, 실제 휴대폰. iOS는 조각 밖으로 미뤘고([harness-design.md](harness-design.md#조각에-넣지-않은-것)), 나머지는 조각 4·5에서 붙입니다(아래 「다음 조각」).

조각 1·2의 원장, 잠금, 관문, 횟수 제한, 실패 원인 분류, PO 창구, 검토 페이지, 패킷은 그대로 씁니다. 새로 만드는 것은 Figma 노드와 그 세션, 프레임 고정, 기기와 빌드, 두 플랫폼의 인수 테스트, 화면 비교입니다.

### 파일 형식

- **`story.md`:** 머리에 `작업 유형: mobile`을 더합니다. 없으면 설정의 `work_type`을 씁니다.
- **`.feature`의 프레임 줄:** 화면 시나리오 위에 `# figma: <node-id>`를 붙입니다(예: `# figma: 12:345` 다음 줄에 `@S15 @R10`). 사람이 읽는 프레임 이름은 시나리오 ID입니다.
- **`states.md`:** 화면 시나리오마다 다섯 상태(성공, 실패, 빈 상태, 로딩, 오류)에 와이어프레임 프레임이나 「해당 없음과 그 이유」를 적습니다.
- **`design/tokens.json`:** Figma 변수를 옮긴 파일입니다(색, 간격, 글꼴, 모서리). `mobile/theme.ts`는 이 값을 씁니다.
- **`design/code-connect.json`:** 컴포넌트마다 Figma 노드와 코드 파일의 짝입니다.
- **`design/frames/`:** 시나리오마다 끝 화면 프레임을 3배(1080×2400)로 받은 이미지(`S15.png`)입니다. N03F만 쓰고, N04 승인 뒤에는 잠깁니다.
- **인수 테스트:** Android는 `tests/e2e/android/S15.yaml`(Maestro 플로우), 웹은 `tests/e2e/web/S15.spec.ts`(Playwright)입니다. 플로우의 마지막 단계에서 화면을 찍습니다.

### `nodes.yaml`에 더하는 것

- **`applies_to`:** 노드가 어느 작업 유형에서 도는지(`[mobile, web]`). 기능의 작업 유형으로 거르고, 맞지 않으면 다음 노드로 건너뜁니다.
- **`figma`:** 노드가 쓸 수 있는 Figma 도구(`write`, `read`, 없음). 어댑터가 이 값으로 작업 세션에 도구를 엽니다.
- **`once: project`:** N00F처럼 프로젝트에 한 번만 도는 노드. 끝났는지는 원장과 파일(`design/tokens.json`)로 봅니다.
- **관문 검사:** `tokens_match`, `code_connect_complete`, `states_complete`, `frames_complete`, `visual_match`, `e2e_files_exist`.
- **`platforms`:** 인수 테스트와 화면 비교를 플랫폼마다 돌립니다. 하나라도 실패하면 그 노드가 실패하고, 원장에는 플랫폼별 결과를 남깁니다.

### 노드 지시문

- **새로 씀:** N00F, N03W, N03F와 리뷰 셋(`N00F.review.md`, `N03W.review.md`, `N03F.review.md`), N26F의 분류 지시문
- **고침:** N13(화면 기능의 설계에 화면과 컴포넌트), N22(플랫폼별 플로우, 마지막에 화면 찍기), N24(고정된 이미지와 Code Connect 컴포넌트로 구현, Figma 출력은 구조 참고용이고 React Native로 옮겨 씀), N27(컴포넌트를 썼는지)
- 디자인 세션 지시문은 Figma 공식 스킬(`figma-use`, `figma-generate-library`, `figma-generate-design`)을 먼저 읽게 합니다(설계 ④).

## 디자인이 흐르는 길

```
N00F 디자인 시스템 ─▶ N03W 와이어프레임 ─▶ N03F 완성 화면 ─▶ N04 사람 승인 ─▶ 프레임 고정 ─▶ N24 구현 ─▶ N26F 화면 비교
```

- **N00F 디자인 시스템:** 변수와 컴포넌트 4개를 Figma에 만들고, 같은 값의 테마와 코드 컴포넌트를 만들어 Code Connect로 잇습니다. 프로젝트에 한 번.
- **N03W 와이어프레임:** 시나리오마다 다섯 상태를 회색 상자로 그립니다. 리뷰 세션이 빠진 상태를 찾습니다.
- **N03F 완성 화면:** 디자인 시스템의 컴포넌트와 변수만 써서 시나리오의 끝 화면을 그립니다. 프레임 이름은 시나리오 ID입니다.
- **N04 사람 승인:** PO가 스펙, 시나리오와 함께 화면 이미지를 한 페이지에서 보고 승인합니다.
- **프레임 고정:** 결정적인 자리입니다. N03F가 받아 둔 프레임 이미지를 PO가 검토 페이지에서 보고 승인하면, 그 이미지의 해시가 패킷에 남습니다. 이 뒤로는 Figma를 누가 고쳐도 기준이 바뀌지 않습니다.
- **N24 구현:** 고정된 이미지와 Code Connect 컴포넌트로 화면을 만듭니다. Figma에는 쓸 수 없습니다.
- **N26F 화면 비교:** 가상 기기와 웹에서 찍은 화면을 고정된 이미지와 비교합니다. 다르면 대부분 구현을 고칩니다(`ui_mismatch`). 프레임 자체가 틀렸을 때만 사람이 승인해 디자인으로 돌아갑니다.

## 화면 비교 (N26F)

- **비교할 것:** 인수 테스트가 플로우 마지막에 찍은 화면(`.4dd/shots/<플랫폼>/S15.png`)과 고정된 프레임(`design/frames/S15.png`)입니다. 크기는 기기에 맞춥니다(Android 1080×2400, 웹은 360×800 화면을 3배로 찍음).
- **판정:** 다른 픽셀의 비율이 허용 비율(기본 5%) 이하이면 통과입니다. 상태 표시줄처럼 매번 바뀌는 영역은 뺍니다. 허용 비율과 뺄 영역은 `4dd.config.yaml`의 `visual`에 있고 잠겨 있습니다(설계 ④).
- **증거:** 실패하면 차이 이미지(`.4dd/shots/diff/<플랫폼>/S15.png`)와 비율을 원장과 관문 출력에 남깁니다. 분류 세션은 이 이미지를 보고 `ui_mismatch`, `code_bug`, `design_wrong` 가운데 하나를 고릅니다.
- **처음 맞추기:** 맞게 구현해도 글꼴 렌더링 때문에 차이가 남습니다. 첫 실행에서 실제 차이를 재고, 5%로 부족하면 기준값을 바꿀지 오너가 정합니다. 에이전트는 기준값을 바꿀 수 없습니다.

## 자기 검토

### 1차 검토에서 찾은 문제와 바꾼 점

- **기준이 움직임:** 처음 안은 N26F가 살아 있는 Figma 프레임과 비교했습니다. 승인 뒤 누가 Figma를 고치면 기준이 바뀝니다. 승인한 이미지를 저장소에 두고 패킷 해시로 지키게 바꿨습니다(G11).
- **순환:** 같은 세션이 그리고 구현하면 화면 비교가 독립 검사가 되지 못합니다. Figma 쓰기 도구를 디자인 노드에만 열고, 구현 세션은 읽기만 하게 했습니다(G10).
- **글꼴 때문에 늘 실패:** Figma의 글꼴과 기기의 기본 글꼴이 다르면 맞게 구현해도 5%를 넘습니다. 디자인 시스템이 Figma와 앱에 같은 글꼴 파일을 쓰게 하고, 첫 실행에서 실제 차이를 재서 기준값은 오너가 정하게 했습니다.
- **비교 도구가 둘:** Maestro와 Playwright의 화면 비교는 방식이 다릅니다. 하네스가 같은 방식으로 비교하게 했습니다.
- **기기 부팅 비용:** 작업마다 기기를 띄우면 50초씩 듭니다. Stage 2 시작에 한 번 띄우게 했습니다.

### 2차 검토에서 찾은 문제와 바꾼 점

- **변수 관문이 막힘:** 디자인 시스템 관문(Figma 변수와 테마가 같은지)을 Figma REST API로 하려 했는데, 변수 읽기는 Enterprise 요금제에서만 됩니다. 디자인 세션이 변수를 파일로 옮기고, 하네스는 파일끼리 비교하고, Figma와 파일이 같은지는 리뷰 세션이 보게 나눴습니다.
- **프레임이 너무 많아짐:** 시나리오 개요(예가 여럿)마다 프레임을 그리면 화면이 크게 늘어납니다. 시나리오마다 끝 화면 프레임 하나로 정하고, 상태(로딩, 오류 같은 것)는 와이어프레임의 체크리스트로 확인하게 했습니다.
- **비개발자 경로:** PO는 Figma를 열지 않아도 됩니다. 화면 이미지와 디자인 시스템이 N04 검토 페이지에 들어갑니다(휴대폰에서 봄).
- **Figma 접근이 도구마다 다름:** Claude는 노드마다 서버를 열고, Codex는 사람이 한 번 등록·로그인합니다. 둘 다 `4dd figma check`로 미리 확인합니다.
- **한 프로젝트에 백엔드와 화면:** 프로젝트 하나에 작업 유형 하나만 두면 로그인 백엔드와 앱 화면을 함께 다룰 수 없습니다. 개발론의 「기능 단위」대로 기능마다 작업 유형을 두게 했습니다.

### 남은 위험

- 화면 비교의 허용 비율이 맞게 구현한 화면을 떨어뜨리거나, 틀린 화면을 통과시킬 수 있습니다. 첫 실행의 분포를 보고 오너가 정합니다.
- Figma 쓰기 도구(`use_figma`)는 베타입니다. 동작이나 요금이 바뀔 수 있습니다.
- 두 플랫폼을 모두 돌리면 Stage 2의 시간과 비용이 늘어납니다. 보고서로 재고, 비싸면 웹을 먼저 돌리는 순서로 줄입니다.
- 디자인 세션의 Figma 그리기는 토큰을 많이 씁니다. 첫 실행에서 노드별 비용을 봅니다.
