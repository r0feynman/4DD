4DD 개발론

4DD는 네 가지 주도 개발(4 Driven Development)을 스크럼 스프린트 안에서 함께 돌리는 앱·웹 개발 방법입니다. 스펙 문서로 무엇을 만들지 정하고, 시나리오와 Figma 화면으로 동작을 정의하고, 단위 테스트로 코드를 확인합니다.

Spec · SDD Behavior · BDD Design · Figma Test · TDD

세 방법의 역할

SDD · 스펙 주도
무엇을, 왜, 어떤 구조로 만드나
산출물: spec.md, design.md, tasks.md
BDD · 행위 주도
사용자 입장에서 어떻게 동작해야 하나
산출물: Given-When-Then 시나리오, Figma 화면 흐름, 인수 테스트
TDD · 테스트 주도
코드 단위로 맞게 동작하나
산출물: 단위 테스트 (Red → Green → Refactor)

스펙에서 시나리오가 나오고, 시나리오를 통과시키기 위해 단위 테스트를 반복합니다. 위에서 아래로 갈수록 범위가 좁아집니다.

BDD를 Figma 화면으로

시나리오의 Given-When-Then은 화면 흐름과 그대로 대응합니다. 시나리오 하나를 Figma 프레임 흐름 하나와 짝지으면, 기획자와 고객이 문장 대신 실제로 움직이는 화면을 보고 합의할 수 있습니다.

BDDFigma예시 (비밀번호 5회 틀림)
Given 상황시작 화면 프레임Login/Default 로그인 화면
When 행동프로토타입 인터랙션비밀번호 입력 후 로그인 버튼 클릭 (5회)
Then 결과도착 화면 프레임Login/Locked 잠금 안내 화면
텍스트 시나리오가 기준입니다. Figma는 시나리오를 대체하지 않고 함께 씁니다. "10분간 잠금", 권한, 데이터 검증처럼 화면에 드러나지 않는 규칙은 텍스트 시나리오에만 남기 때문입니다.
성공 화면만 그리지 않습니다. 실패, 빈 상태, 로딩, 네트워크 오류 화면도 시나리오마다 같이 만듭니다.

지켜야 할 규칙

스펙이 기준

코드와 스펙이 다르면 둘 중 하나를 고칩니다. 둘이 어긋난 채로 두지 않습니다.

스펙은 계속 갱신

리뷰에서 나온 피드백은 spec.md에 반영합니다. 스펙은 끝까지 살아 있는 문서입니다.

Figma도 스펙의 일부

디자인이 바뀌면 시나리오와 인수 테스트도 같은 스프린트 안에서 함께 고칩니다. 화면과 시나리오가 어긋난 채로 두지 않습니다.

DoD에 네 가지 모두

시나리오 전부 통과, 새 코드는 단위 테스트 포함, CI 통과, 화면이 Figma 프레임과 일치. 넷 다 충족해야 완료입니다.

폴더 구조 예시

specs/
  login/
    spec.md        # 요구사항 (SDD)
    design.md      # 설계 (SDD)
    tasks.md       # 작업 목록 (SDD)
    login.feature  # 시나리오 (BDD) + Figma 프레임 링크
src/
tests/
  unit/            # 단위 테스트 (TDD)
  acceptance/      # 인수 테스트 (BDD, E2E)
  visual/          # Figma 프레임과 스크린샷 비교

시나리오 파일에는 프레임 링크를 주석으로 남겨 둡니다.

# figma: https://figma.com/design/…?node-id=12-34
시나리오: 비밀번호 5회 틀림
  Given 로그인 화면에서          # 프레임: Login/Default
  When  비밀번호를 5번 틀리면
  Then  잠금 안내가 보인다         # 프레임: Login/Locked

Figma MCP를 연결하면 Claude가 프레임을 직접 읽고 시나리오와 화면 코드 초안을 만들 수 있습니다.

4DD 스프린트 노드 맵

스프린트 한 바퀴를 스테이지 다섯 개로 나누고, 각 스테이지 안에 노드를 배치했습니다. 노드 색은 방법론을, 마름모는 판단 노드를, 점선은 스펙이나 디자인을 바꿔야 할 때의 되돌림을 뜻합니다.

스프린트 (한 바퀴, 1~4주)
 └─ 스테이지 (Stage 0~4)
     └─ 노드 (N01, N26F …)
