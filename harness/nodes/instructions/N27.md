# N27 설계 스펙과 일치? (별도 리뷰 세션)

## 목표
이 작업에서 바뀐 코드가 `design.md`와 맞는지 판정합니다. 당신은 코드를 쓴 세션과 다른 리뷰 세션입니다.

## 할 것
- 「이번 작업」의 변경분과 `design.md`만 봅니다. 파일 위치, 내보내는 함수, API 경로와 응답, 데이터 모델, 결정 사항을 대조합니다.
- 어긋난 곳은 파일과 줄, 그리고 설계의 어느 부분과 다른지 적습니다.
- 원인을 고릅니다.
  - `code_bug`: 설계대로 고치면 맞출 수 있음 (코드를 고침)
  - `arch_wrong`: 설계대로는 구현할 수 없음 (설계를 고쳐야 함, 사람 승인)
- `code_bug`이면 고칠 곳(`fix_in`)도 답합니다.
  - `behavior`: 동작이 설계와 다름 (N23에서 실패하는 단위 테스트부터)
  - `structure`: 동작은 맞고 구조(파일 위치, 함수 이름, 데이터 모델)만 설계와 다름 (N25에서 동작을 바꾸지 않고 정리)
  - `acceptance_test`: 구현은 맞는데 인수 테스트가 시나리오를 제대로 확인하지 않음 (N22에서 인수 테스트를 고침)
  - `unit_test`: 동작은 설계대로 구현됐는데, 설계가 단위 테스트로 확인하라고 한 그 동작의 테스트가 없음 (N23에서 테스트만 더하고 다시 리뷰. 구현이 이미 있으므로 새 테스트는 처음부터 통과함)
  - 고칠 곳은 지적한 파일을 고칠 수 있는 노드로 고릅니다: `tests/e2e/`·`tests/acceptance/`의 파일(위치, 공용 파일 포함)은 `acceptance_test`, `tests/unit/`은 `unit_test`, `src/`·`mobile/`은 `structure`나 `behavior`. 여러 곳에 걸치면 고칠 것이 많은 쪽을 고릅니다. 나머지는 다음 리뷰가 다시 잡습니다.

- 화면 작업이면 화면 코드와 부품 코드(`mobile/ui/`)가 테마 값만 쓰는지(고정 색·간격·글자 크기가 없는지) 봅니다. 어기면 `code_bug`, `structure`입니다.
- 「이미 충족된 작업」이면 인수 테스트가 시나리오를 실제로 확인하는지도 봅니다. 구현을 바꾸지 않고 넘어온 작업이라 이것이 유일한 안전장치입니다.

## 하지 말 것
- 파일을 고치지 않습니다. 이 세션은 읽기 전용입니다.
- 설계에 없는 취향(이름 짓기, 스타일)으로 실패시키지 않습니다.

## 끝낼 때
정해진 출력 형식으로 통과 여부, 원인, 지적 목록을 답합니다. 지적(why)은 한국어로 씁니다. 사람이 회고에서 읽기 때문입니다.
