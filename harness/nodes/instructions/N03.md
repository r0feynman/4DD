# N03 시나리오 작성

## 목표
「이번 기능」의 요구사항마다 Given-When-Then 시나리오를 씁니다. 인수 테스트(N22)가 이 시나리오를 그대로 따라갑니다.

## 할 것
- 파일은 `specs/<기능>/<기능>.feature` 하나입니다. 첫 줄에 `# language: ko`를 쓰고, 한국어 키워드(기능, 배경, 시나리오, 조건, 만일, 그러면, 그리고)를 씁니다.
- 시나리오마다 위에 `@S5 @R4`처럼 시나리오 ID 하나와 그 시나리오가 검증하는 요구사항 ID를 붙입니다. 시나리오 번호는 「이번 기능에서 쓸 ID」의 다음 번호부터 이어 씁니다.
- 모든 요구사항에 시나리오가 하나 이상 있어야 합니다. 성공하는 경우와 실패하는 경우(잘못된 입력, 만료, 잠금 같은 것)를 함께 씁니다.
- 화면이 없는 작업 유형이면 화면 대신 API 요청과 응답(상태 코드, 응답 내용)으로 확인하게 씁니다.
- 시간이 들어가면(만료, 잠금) 시간을 흘려보내는 단계를 분명히 씁니다(예: "만일 31분이 지난 뒤 …").
- 「PO의 말」이나 「지난 관문 출력」이 있으면 그것부터 반영합니다.
- 예시 값(아이디, 비밀번호, 시간, 금액)은 요구사항의 모든 규칙을 따르게 씁니다. 성공하는 시나리오의 예시는 모든 규칙을 채우고, 실패하는 시나리오의 예시는 그 시나리오가 확인하는 규칙 하나만 어기게 씁니다. 스펙이 바뀌어 다시 쓸 때는 새로 생긴 규칙에 맞게 **기존 시나리오의 예시 값도** 다시 봅니다(2026-11-26 실제 실행: 아이디 4~20자 규칙이 생겼는데 앞 시나리오의 예시 아이디 `lee`(3자)를 그대로 두어 개발 중에 멈춤).

## 하지 말 것
- `.feature` 밖을 고치지 않습니다. 스펙, 설계, 다른 기능은 잠겨 있습니다.
- 스펙에 없는 동작을 시나리오에서 새로 정하지 않습니다. 모자라면 실패한 관문이나 리뷰가 알려 줍니다.
- 커밋하지 않습니다.

## 끝낼 때
시나리오 수와 각 시나리오의 ID를 한 줄로 답합니다.
